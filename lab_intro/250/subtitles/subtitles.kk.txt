Қайырлы күн, құрметті студенттер! Зертханалық жұмыстың кезекті шолу сессиясына қош келдіңіздер. Бүгінгі зертханалық жұмыстың тақырыбы — AWS бұлтында жоғары қолжетімді IT-инфрақұрылым құру. Ендеше, бастайық. Алдымен тиісті курсты ашуымыз керек — бұл AWS Academy Cloud Architecting, содан кейін модульдер тізімін ашамыз. Бізді тоғызыншы модуль қызықтырады, және сол модульде Guided Lab белсенділігі бар. Зертханалық жұмыстың басты парақшасына өту үшін оны ашайық. Бұл белсенділік зертханалық жұмыстың шолуы болғандықтан, терминал терезесі бізге қажет емес, сондықтан оны жасырып, тапсырма мәтінін парақшада толық көрсетуге болады. Енді зертханалық жұмыстың негізгі бөлігін бастаймыз. Бұл зертханалық жұмыстың мақсаты — осы AWS аккаунттағы VPC-дің ағымдағы күйін шолу. Содан кейін біз Application Load Balancer құрамыз, Auto Scaling Group құрамыз және олардың дұрыс жұмыс істеп, жоғары қолжетімділікті қамтамасыз ететінін тексереміз. Зертханалық жұмыстың соңында біз AWS бұлтында келесі IT-инфрақұрылымды құрамыз: бір аймақ, екі Availability зона, бір VPC, 4 subnets — 2 Public subnet және 2 Private subnet. Біз Application Load Balancer мен Auto Scaling Group құрамыз, олар екі түрлі Availability зонадағы EC2 инстанстарға трафикті теңестіретін болады. Бұл зертханалық жұмысты орындауға 40 минут ұсынылады, қажет болған жағдайда таймерді қайта бастап, зертханалық жұмысты орындау уақытыңызды ұзартуға болады. Бұл үшін қосымша айыппұл салынбайды, ең бастысы — барлық тапсырмаларды орындап, максималды ұпай жинау. Сондай-ақ еске саламыз, біз құмжәшігінде жұмыс істейміз, бұл арнайы жасалған AWS аккаунт, ол зертханалық сессия аясында уақытша жасалады және біраз шектеулерге ие. Зертханалық жұмыстың аясындағы барлық қажетті сервистер мен олардың функциялары қолжетімді, ал қалғандары өшірілуі мүмкін. Сіз нақты AWS аккаунтында жұмыс істегенде бұл шектеулер болмайды, бірақ онда жұмыс істеуде абай болу керек. Зертханалық жұмысты бастау үшін алдымен экранның жоғарғы оң жақ бөлігіндегі Start Lab батырмасын басу қажет. Уақытша AWS аккаунтты жасау процесі басталады, дайын болғаннан кейін тиісті хабарлама шығады. Содан кейін қалқымалы терезені жабуға болады және AWS батырмасын басқанда (экранның жоғарғы оң жағында) жаңа қойындыда уақытша жасалған AWS аккаунтына өтуге болады. Біз бірінші тапсырманы бастаймыз. Бірінші тапсырма — уақытша AWS аккаунтта алдын ала жасалған VPC ресурстары мен компоненттерін зерттеу. Бұл слайдта сіз осы ресурстарды көре аласыз, енді AWS Management Console-ды пайдаланып, бұл ресурстарды егжей-тегжейлі көреміз. Ең алдымен VPC сервисіне кіру қажет. Өткен соң, VPC бойынша фильтр жасау мүмкіндігі бар, LabVPC бойынша фильтр жасайық. Бұл жағдайда сол жақтағы навигациялық мәзір арқылы өтетін барлық парақшалар LabVPC-мен байланысты ресурстарды көрсетеді, бұл өте ыңғайлы. Енді VPC тізіміне өтейік, біз тек бір ғана VPC көреміз — LabVPC. CIDR блогына назар аударыңыз — бұл 10.0.0.0/16, яғни шамамен 65 мың IP-адресті қамтиды. Сіз паттернді көріп тұрсыз: 10.0.x.x, мұнда x — динамикалық бөлік. Сол жақтағы навигациялық мәзірді пайдаланып, subnets тізімін ашайық. Біз барлығы 4 subnets фильтрленгенін көреміз, олар екі availability зонаға бөлінген. Мысал үшін public subnet 1 таңдайық, оның LabVPC-ке байланысқанын көреміз, CIDR блогы — 10.0.0.0/24, яғни 256 IP-адресті қамтиды. Келесі қадам — Route table қойындысын ашайық, онда екі rule бар. Біріншісі — VPC ішіндегі ресурстардың өзара әрекеттесуі үшін, екіншісі — Internet Gateway арқылы интернетке шығу үшін. Сондықтан Destination ретінде CIDR блок барлық нөлдер көрсетілген, ал Target ретінде Internet Gateway қолданылып отыр. Осы rule арқасында public subnet шын мәнінде public болып, интернеттен қолжетімді болады. Егер Network ACL қойындысын ашсақ, онда әдепкі rules көрсетілген — олар кіріс және шығыс трафикті рұқсат етеді. Сол жақтағы навигациялық мәзірді пайдаланып, Internet gateways тармағына өтсек, бір ғана фильтрленген Internet Gateway көреміз — Lab IG, ол Lab VPC-ге байланысқан. Содан кейін қайтадан навигациялық мәзірден Security groups тізіміне өтсек, онда Inventory-DB security group көрсетіледі. Бұл дерекқордың кіріс трафигін бақылайтын security group. Егер осы security group-тың inbound rules ашсақ, онда 3306 порты арқылы трафикке рұқсат беретін ереже бар екенін көреміз. Бұл — MySQL немесе Aurora дерекқор трафигі, біздің Lab VPC ішінде болған кезде кез келген IP-адрестерінен. Сәл кейінірек біз оны тек қана біздің қолданба серверлерінен келетін трафикке рұқсат ететіндей етіп өзгертеміз. Егер осы security group үшін outbound rules ашсақ, мұнда әдепкі мәндер көрсетілген және барлық шығыс трафигіне рұқсат етілген. Біз зертханалық жұмыстың екінші тапсырмасын бастаймыз және Application Load Balancer құрамыз. Қолданбаңызды жоғары қолжетімді ету үшін ресурстарды бірнеше availability зонаға тарату ұсынылады, кемінде екі availability зона. Идеясы — әрбір availability зона — бұл жеке тұрған бір немесе бірнеше физикалық дата-центрлер. Жүктемені бірнеше availability зонаға таратқанда, сұраулар мүлде бөлек, бір-біріне тәуелсіз физикалық дата-центрлерге кетеді. Егер бір availability зонада ақау болса, пайдаланушылар бұл ақауды байқамайды, өйткені барлық трафик жұмыс істеп тұрған availability зонаға ауыстырылады. Ақауы бар availability зона қайта қалпына келген соң, жүктеме барлық availability зоналар арасында тең бөлінеді. Бірнеше availability зонаның бірден істен шығу ықтималдығы өте төмен, сондықтан бұл жоғары қолжетімділікті қамтамасыз етудің бірінші және негізгі қадамы. AWS ішінде жоғары қолжетімділікті іске асырудың best practice шешімі — бұл Elastic Load Balancing сервисі немесе қысқаша ELB. Оның үш түрі бар: ALB (Application Load Balancer), NLB (Network Load Balancer) және Classic Load Balancer, ол тек артқа үйлесімділік үшін сақталған және қазір жаңа түрде жасалмайды. Бұл зертханалық жұмыста біз Application Load Balancer құрамыз. Осы диаграммада тапсырма аяқталған соң бізде жаңа ресурс пайда болатынын көріп отырсыз: Application Load Balancer, ол аймақ деңгейінде жұмыс істеп, трафикті екі availability зона арасында тарататын болады. Енді, бұл тапсырманы орындау үшін қажетті қадамдарды бірге қарап шығайық. Алдымен сервис іздеу жолағын пайдаланып, EC2 енгіземіз. EC2 сервисінің басты парақшасына кірген соң, сол жақтағы навигация мәзірінен Load Balancers тармағын таңдаймыз. Load Balancers тізімін көреміз, ол әдетте бос болады. Бірақ бәрібір экранның жоғарғы оң жағындағы Create Load Balancer батырмасын басу қажет болады. Біз жаңа парақшаға өтеміз, алдымен Load balancer түрін таңдау керек болады. Біз Application Load Balancer құрамыз, сондықтан бұл бөлімде төменгі жағындағы Create батырмасын басамыз. Келесі парақшада Load balancer баптауларын енгізуіміз қажет: Load balancer name ретінде Inventory-LB енгіземіз, мұндағы LB — Load Balancer қысқартылған түрі. Сәл төменде Network mapping бөлімі бар, мұнда біздің VPC таңдау қажет — Lab VPC. Оны таңдаған соң, қолданылатын availability зоналарды көрсету керек, әр availability зона үшін тиісті subnet таңдау қажет. Бұл зертханалық жұмыс аясында біз public subnets пайдаланамыз, сондықтан алдымен бірінші availability зонадан public subnet 1 таңдаймыз. Содан соң екінші availability зонадан public subnet 2 таңдаймыз. Бұл бөлім бойынша баптаулар дұрыс жасалды, келесі бөлімге өтеміз. Бұл Security groups бөлімі, мұнда жаңа security group құру қажет болады, сәйкес сілтеме болады. Сілтемеге басқан соң, жаңа браузер қойындысы ашылады, онда жаңа security group құрамыз, сосын қайтадан Load balancer құру парақшасына ораламыз. Қазір біз жаңа security group құру парақшасындамыз. Security group name ретінде Inventory-LB, Description ретінде Enable web access to load balancer енгіземіз, VPC ретінде Lab VPC таңдаймыз және төменде rules құрамыз. Бізді Inbound rules қызықтырады, екі inbound rule құрамыз. Біріншісі — HTTP трафигі, ол кез келген IPv4 IP-адрестен қолжетімді болады. Келесі rule — HTTPS үшін, яғни қорғалған HTTP трафигі, мұнда да Source ретінде Anywhere-IPv4 көрсетіледі. Create security group батырмасын басамыз және енді алдыңғы қойындыға оралу қажет болады. Жаңарту батырмасын басып, security groups тізімін жаңартамыз, сонда Inventory-LB тізімнен шығады және оны таңдаймыз. Келесі бөлім — Listeners and routing бөліміне өтеміз. Бұл бөлімде трафиктің қалай бағытталатыны сипатталады. Бұл жерде біз load balancer-ді target топтарға байланыстырамыз. Target топты әлі құрмағандықтан, Create target group сілтемесін басамыз, ол бізді жаңа браузер қойындысына апарады. Бұл жерде біз security group секілді target топты бөлек құрамыз. Target ретінде Instances таңдаймыз, Target group name ретінде Inventory-App енгіземіз, VPC ретінде Lab VPC таңдаймыз. Төменгі бөлікте Advanced health check settings бөлімі бар, оны ашып, бірнеше өзгеріс енгіземіз. Healthy threshold — 2, Interval — 10 деп қоямыз. Бұл дегеніміз — әр 10 секунд сайын тексеру орындалады және екі рет қатарынан сәтсіз болса, target Unhealthy ретінде белгіленеді. Керісінше, екі рет қатарынан сәтті болса, инстанс Healthy деп саналады және оған трафик бағытталады. Барлығын баптағаннан кейін, парақшаның төменгі жағына жылжып, Create target group батырмасын басу қажет. Енді Load balancer құру қойындысына ораламыз, сол жерде Refresh батырмасын басып, жаңа target топтар тізімін жаңартамыз. HTTP протоколы және 80-порт үшін Listeners бөлімінде Default action ретінде жаңа құрылған Inventory-App target тобын таңдаймыз. Парақшаның төменгі жағына түсіп, Create load balancer батырмасын басамыз. Осы арқылы load balancer сәтті құрылады және үшінші тапсырмаға өте аламыз. Біз зертханалық жұмыстың үшінші тапсырмасына жеттік, мұнда Auto Scaling group құрамыз. Auto Scaling group — бұл біздің IT-инфрақұрылымымызға динамика беретін ресурс және ол EC2 инстанстарын құру немесе жою қажеттігін шешеді. Ол Load balancer-мен тығыз байланыста жұмыс істейді. Бұл тапсырма екі бөлімнен тұрады, бірінші бөлігінде біз Auto Scaling group үшін AMI құрамыз. Ол үшін EC2 сервисіне өтіп, сол жақтағы навигациялық мәзір арқылы инстанстар тізіміне кіреміз. Инстанстар тізімінен Web Server 1 тауып, оның екі жүйелік тексеруден сәтті өткенін тексереміз. Содан кейін Web Server 1 таңдап, жоғарғы оң жақтан Actions батырмасын басамыз, ашылған мәзірден Image and templates, содан кейін Create image таңдаңыз. Бұл EC2 инстансынан жаңа image жасаймыз. Image name ретінде Web Server AMI, Description ретінде Lab AMI for Web Server деп енгіземіз. Содан кейін Create image батырмасын басамыз. Жасыл хабарламада AMI сәтті жасалғанын көреміз және біз келесі тапсырмада пайдаланатын AMI ID-ні аламыз. Енді зертханалық жұмыстың екінші бөлігіне өтеміз, мұнда Launch Template құрамыз. Launch Template — бұл AMI-ден бөлек бірқатар параметрлерді сипаттайтын ресурс. Launch Template арқылы Auto Scaling group автоматты түрде жаңа EC2 инстанстарын тіркей алады. Қадамдар бойынша өтейік: сол жақ навигация мәзірінен Launch Template тармағын таңдаймыз. Create Launch Template батырмасын басып, ашылған қойындыда келесі ақпаратты енгіземіз. Launch Template name ретінде Inventory-LT, Auto Scaling guidance үшін құсбелгі қойып, AMI ретінде Web Server AMI таңдаймыз. Instance type ретінде t2.micro таңдаймыз, Key pair name ретінде vockey енгіземіз. Бұл кілтті зертханалық жұмыстың парақшасынан жүктеуге болады. Security groups бөлімінде бар security group пайдаланамыз және тізімнен Inventory-App таңдаймыз. Парақшаның төменгі жағына жылжып, Advanced details бөлімін ашамыз. IAM instance profile өрісіне Inventory-App-Role енгіземіз. Төменірек, Detailed CloudWatch monitoring үшін құсбелгі қоямыз. Парақшаның ең төменгі жағында User data деп аталатын өріске командалар жиынын қойып, web server-ге демо қолданбаны орнатамыз. Барлық қажетті деректер енгізілді, енді Create launch template батырмасын басамыз. Template жасалған соң, ол сәтті жасалғаны туралы хабарлама көреміз. Inventory-LT таңдап, Actions → Create Auto Scaling group батырмасын басамыз. Бізді жаңа қойындыға бағыттайды, онда жаңа Auto Scaling group үшін ақпарат енгіземіз. Auto Scaling group name ретінде Inventory-ASG, Launch template ретінде Inventory-LT енгізіп, Next батырмасын басамыз. Екінші парақшада жаңа Auto Scaling group желі баптауларын көрсетеміз. VPC ретінде Lab VPC, Availability зоналар ретінде us-east-1a және us-east-1b таңдаймыз, әрқайсысы үшін сәйкес subnet. Бұл — private subnet 1 және private subnet 2, сонда жаңа инстанстар екі availability зонадағы private subnet ішінде жасалады. Next батырмасын басып, үшінші парақшаға өтеміз. Мұнда Auto Scaling group-ті бар Load balancer-ге байлаймыз. Біз Load balancer емес, target топты таңдаймыз, осылайша олар бір-біріне байланысады. Ашылмалы тізімнен Inventory-App таңдаңыз. Health checks бөлімінде Health check grace period үшін 90 секунд көрсетеміз. Қосымша баптаулар ішінде Enable group metrics collection within CloudWatch өрісіне құсбелгісін қойыңыз. Бұл метрикаларды әр минут сайын алуға мүмкіндік береді және Auto Scaling жылдамырақ жауап береді. Экранның төменгі жағында Next батырмасын басыңыз. Төртінші парақшада Auto Scaling group өлшемдерін көрсетеміз, сондай-ақ Scaling policies болса, оларды баптаймыз. Desired capacity ретінде 2, Minimum capacity ретінде 2, Maximum capacity ретінде 6 енгіземіз. Бұл зертханалық жұмыстың тапсырмасында қате бар, минимум — 2, максимум — 6 инстанс болуы тиіс. Auto Scaling group құрылған кезде, бірден 2 EC2 инстанс пайда болады. Scaling policies ретінде None таңдап, Next батырмасын басамыз. Бесінші парақшада әртүрлі хабарландыруларды баптауға болады, бірақ зертханалық жұмыс аясында ол қажет емес, сондықтан Next басамыз. Келесі парақшада тегтерді баптауды ұсынады, келесіде осыны істейміз. Key ретінде Name, ал Value ретінде Inventory-App көрсетеміз, бұл тегтер жаңа EC2 инстанстарға да қолданылады және осылайша сіз оларды басқа инстанстардан оңай ажырата аласыз. Келесі парақшаға өту үшін Next батырмасын басамыз, онда алдыңғы парақшаларда енгізілген барлық параметрлердің тізімі көрсетіледі. Егер барлық параметрлер дұрыс болса, экранның оң жақ төменгі бөлігінде Create Auto Scaling group батырмасын басу қажет. Auto Scaling group біраз уақыт ішінде құрылады, және бастапқыда бұл топқа тіркелген инстанстар саны 0 болуы қалыпты жағдай. Біз Desired capacity ретінде 2 деп көрсеткендіктен, біраз уақыттан кейін жаңа 2 EC2 инстанс құрылады. Мұнда Auto Scaling group жалпы тізімінде қалай көрсетілетінінің мысалын көре аласыз. Статус Updating capacity болады, инстанстар саны 0, сонымен қатар Desired, Minimum және Maximum capacity көрсетіледі. Біраз уақыт өткен соң Refresh батырмасын немесе парақшаны жаңартуға болады және статус Available болып өзгеріп, инстанстар саны 2 болады. Егер осылай болса, үшінші тапсырманы сәтті аяқтадық деген сөз және келесіге өте аламыз. Біз зертханалық жұмыстың төртінші тапсырмасына келдік және мұнда Security топтарын жаңартамыз. Диаграммада көрсетілгендей, интернеттегі қолданушылар HTTP немесе HTTPS трафикті Load balancer-ге жібереді. Бірақ сұрау load balancer-ге жетпей тұрып, security group арқылы өтеді, егер ол рұқсат берсе, сұрау load balancer-ге жетеді, ал егер ереже болмаса, сұрау өтпейді. Жарайды, әрі қарай. Сұрау Application Load Balancer-ге жеткен кезде, ол HTTP трафикті application серверлерге жібереді. Application серверлер бұл сұрауды тек сәйкес security group рұқсат берген жағдайда ғана алады. Application серверлер дерекқормен тығыз байланысты жұмыс істейді, яғни дерекқорға трафик жібереді және дерекқор инстансы да security group-пен байланысқан. Егер security group кіріс трафикке рұқсат берсе, онда сұрау дерекқорда өңделеді, әйтпесе ол қабылданбайды. Осылайша, бұл тапсырма аясында біз барлық security топтарды қарап шығып, қажет болса өзгертеміз. Бірінші security group — бұл load balancer-ге арналған топ, оны біз load balancer құрғанда дұрыс етіп баптадық. Есіңізде болса, ол кез келген кіріс HTTP және HTTPS трафикке рұқсат береді. Содан кейін load balancer бүкіл трафикті target group-ке бағыттайды. Ал Auto Scaling group жаңа EC2 инстанстар құрғанда оларды дәл осы target group-ке тіркейді. Келесі security group — бұл Application security group. Мұнда біраз өзгеріс керек, тек load balancer-ден келетін трафикке рұқсат беру қажет. Ол үшін EC2 сервисінде сол жақтағы навигация мәзірінен Security groups тармағын таңдаймыз. Мұнда Inventory-Apps деген security group таңдаймыз, экранның төменгі жағында бірнеше қойынды ашылады. Бізге Inbound rules қойындысы қажет, мұнда ешқандай ереже жоқ, сондықтан load balancer-ден келетін HTTP трафикке рұқсат беру үшін жаңа ереже қосамыз. HTTPS трафикті қосуымыздың қажеті жоқ, себебі load balancer мен application серверлер бір инфрақұрылымда орналасқан, сондықтан олардың арасында қорғалған трафик жасаудың қажеті жоқ. Одан бөлек, HTTPS трафик көбірек есептеу ресурстарын қажет етеді және баяу жұмыс істейді, сондықтан HTTP және HTTPS трафикті load balancer жағында қабылдаған жөн. Ал load balancer мен application серверлер арасындағы трафик тек HTTP арқылы жүруі керек, бұл — best practice. Ол үшін Edit inbound rules батырмасын басу қажет. Біз жаңа rule қосамыз, Type ретінде HTTP таңдаймыз, Source ретінде Custom көрсетеміз және тиісті жолда sg деп жазуды бастаймыз. Осы жерде барлық security group тізімі көрсетіледі, бізге load balancer-ге тиесілі security group — Inventory-LB таңдау қажет. Description ретінде Traffic from load balancer деп көрсетейік, кейін бұл rule не үшін құрылғанын еске түсіру оңай болу үшін. Экранның оң жақ төменгі бөлігінде Save rules батырмасын басу қажет. Осылайша, екінші security group бапталды және енді біздің веб-серверлер тек load balancer-ден келген трафикті қабылдай алады. Бұл rule құрамына автоматты түрде жүргізілетін health check-тер де кіреді, олар веб-серверлердің қолжетімділігін тексереді. Бізде соңғы security group қалды — бұл дерекқордың security group-ы. Қазіргі уақытта бұл топта жалғыз inbound traffic ережесі бар, ол 3306 порты бойынша VPC ішіндегі кез келген IP-адреске рұқсат береді. Бұл жақсы rule, бірақ біз оны жақсарта аламыз, сол себепті security group тізімінен Inventory-DB тобын таңдаймыз. Содан кейін Inbound rules қойындысын ашып, Edit inbound rules батырмасын басамыз. Енді қолданыстағы rule-ды өшіріп, орнына жаңасын жасауымыз керек. Ол үшін Add rule батырмасын басамыз, Type ретінде MYSQL/Aurora таңдаймыз — порт автоматты түрде 3306 болады. Source ретінде Custom таңдаймыз және келесі жолда sg деп жазамыз — жүйе қолжетімді security group-тарды көрсетеді. Мұнда Inventory-App тобын таңдаймыз. Description ретінде Traffic from application servers деп жазайық — бұл rule не үшін құрылғанын есте сақтау үшін. Экранның оң жақ төменгі бөлігінде Save rules батырмасын басамыз. Біз барлық security group-тарды жаңарттық және қазір үш деңгейлі қорғаныс бар — әрбір келесі деңгей тек алдыңғы деңгейдегі күтілетін ресурстардан трафик қабылдай алады. Бірінші деңгей — интернет, ол load balancer-ге жүгінеді. Бірақ тек load balancer-дің security group-ы рұқсат берген жағдайда ғана ол сұранысты қабылдайды. Келесі, load balancer трафикті біздің application серверлерге таратады. Бірақ трафик application серверлерге тек олардың security group-ы рұқсат берсе ғана жетеді. Бұл топ тек load balancer-ден келген трафикке рұқсат береді, басқа трафик өтпейді. Содан кейін, application серверлер қажет болған жағдайда, яғни бағдарламаның логикасына сәйкес, дерекқорға жүгінеді. Дерекқор жағында да security group бар және ол тек application серверлерден келетін трафикке рұқсат береді. Біз зертханалық жұмыстың бесінші тапсырмасына жеттік және қазір біздің қосымшамызды тестілеуді бастаймыз. Бірінші кезекте, сол жақтағы навигациялық мәзір арқылы Target groups бөліміне өтеміз. Содан кейін тізімнен біздің target топты таңдаймыз — Inventory-App. Негізгі парақша ашылған соң, төменгі бөлігінде бірнеше қойынды көрінеді. Бізге Targets қойындысы қажет. Екі тіркелген таргет болады және екеуі де Healthy күйінде болуы тиіс. Сондай-ақ, таргеттеріміз екі availability зонаға бөлінгенін байқайсыз. Жақсы, енді навигациялық мәзірден Load balancers бөлімін таңдай аламыз. Одан кейін біз Inventory-LB атты load balancer-ді таңдаймыз және DNS name көшіре аламыз — бұл біздің load balancer-дің URL-адресі. Оны жаңа браузер қойындысында ашайық, сонда instance ID мен availability зона көрсетіледі. Парақшаны бірнеше рет жаңартып көріңіз немесе дәл сол сілтемені басқа браузерде ашыңыз, сонда instance ID мен availability зона өзгеретінін байқайсыз. Бұл біздің сұраныстарымыз екі availability зонадағы инстанстарға кезекпен бағытталып жатқанын білдіреді. Біз зертханалық жұмыстың алтыншы тапсырмасына жеттік және қазір орнатқан жоғары қолжетімділікті тестілеуді бастаймыз. Оны тексеру үшін біз EC2 инстанстарының бірін terminate жасап, әрі қарай не болатынын бақылаймыз. Ең алдымен, load balancer-дің URL-адресін көшіріп, оны жаңа браузер қойындысында ашуымыз қажет. Парақша ашылған соң, сұранысты өңдеген instance ID мен availability зонасын есте сақтау қажет. Бұл қойындыны ашық күйде қалдырып, AWS Management Console парақшасына қайта ораламыз. Онда EC2 сервисіне өтіп, Instances тізімін ашып, нақты Inventory-App деп аталатын инстансты және қажетті availability зонасындағысын табамыз. Осы инстансты таңдап, оң жақ жоғарғы бөлігінде Instance state батырмасын басамыз, ашылған тізімнен Terminate instance-ті таңдап, жоюды растау қажет. Енді ең қызықты сәт басталады — load balancer-дің URL-адресі ашық тұрған парақшаға оралып, парақшаны үнемі жаңартып отырамыз. Қате шыға бастайды — бұл қалыпты жағдай, себебі EC2 инстанс қолжетімсіз, сұраныстарды өңдей алмайды, ал load balancer оны әзірге Unhealthy деп белгілемеген. Бір минуттай уақыт өткен соң load balancer бұл инстансты unhealthy деп белгілеп, барлық трафикті екінші инстансқа бағыттайды. Сол кезде веб-қосымша парақшасы қайта ашылады, бірақ instance ID мен availability зонасы өзгеше болады. Енді сіз қанша рет парақшаны жаңартсаңыз да, инкогнито режимде ашсаңыз да, не болмаса браузерді ауыстырсаңыз да, барлық сұраныстар бір нақты инстанстан келіп түседі. Екінші инстанс қалпына келгенше осылай болады. Ол автоматты түрде екінші availability зонада көтеріледі және load balancer-ге қосылған сәттен бастап, трафик екі EC2 инстанс арасында теңдей бөлінеді. Сол кезде сіздің сұраныстарыңыз екі availability зонадағы инстанстар арасында кезектесіп өңделетінін байқайсыз. Біз зертханалық жұмыстың барлық негізгі тапсырмаларын сәтті аяқтадық. Қосымша ретінде екі ерікті тапсырма ұсынылады, олар бағаланбайды, бірақ қалауыңыз бойынша орындай аласыз. Бірінші ерікті тапсырма — дерекқорымыздың жоғары қолжетімділігін баптау. Егер біз IT-инфрақұрылым диаграммасына қарасақ, онда барлық ресурстар дерлік екі availability зонаға бөлініп, жоғары қолжетімділікке ие екенін көреміз. Бірақ дерекқор тек бір availability зонада орналасқан. Егер осы availability зонада немесе нақты осы инстанста ақау орын алса, онда біздің бүкіл IT-инфрақұрылымымыздың жоғары қолжетімділігі пайдасыз болады. Сондықтан бұл әлсіз буынды жою керек және дерекқорды да жоғары қолжетімді етіп жасау қажет. Amazon RDS сервисі мұны жасауға мүмкіндік береді. Енді мұны қалай жасауға болатынын қадамдап қарастырайық. Бірінші кезекте, сервис іздеу жолын қолданып, RDS деп теріп, тиісті сервиске кіреміз. Сервис басты парақшасы ашылады, мұнда сол жақтағы навигациялық мәзірден Databases бөлімін таңдаймыз. Бұл AWS аккаунтындағы барлық дерекқорлар тізімі көрсетіледі, көбінесе бір ғана инстанс болады — бұл біздің Inventory-DB деп аталатын дерекқорымыз. Осы ресурсты ашып, оң жақ жоғарғы бұрыштан Modify батырмасын басайық. Сонда дерекқор ресурсын өңдеу парақшасы ашылады. Мұнда Availability and durability секциясына дейін түсу қажет. Одан кейін Multi-AZ deployment ішінен Create a standby instance таңдаймыз. Standby instance деген не? Бұл — басқа availability зонада пассивті режимде жұмыс істейтін дерекқор инстансы, ал негізгі инстанс белсенді түрде трафикті өңдейді. Егер қандай да бір проблема туындаса, не бүкіл availability зонамен, не болмаса негізгі дерекқор инстансымен, онда трафик автоматты түрде standby instance-ке ауысады. Бұл кезде дерекқор адресі өзгермейді. Бұл өзгеріс сіздің веб-қосымшаларыңыз үшін көрінбейді, яғни бәрі автоматты түрде орын алады. Осылайша дерекқордың жоғары қолжетімділігі қамтамасыз етіледі. Standby instance өлшемі дәл сондай немесе сәл кіші болуы мүмкін. Мұны баптауға болады, біз зертханалық жұмыс аясында db.t3.small өлшемін көрсетеміз, ал деректер үшін бөлінетін дискілік кеңістік (Allocated storage) ретінде 10 гигабайт көрсетеміз. Енді парақшаның ең соңына дейін өтіп, Continue батырмасын басу қажет. Содан соң өзгерістерді кесте бойынша немесе бірден енгізу ұсынылады. Бұл зертханалық жұмыс аясында біз өзгерістерді бірден енгіземіз. Осыдан кейін инстанс Modifying күйіне өтеді және ол басқа availability зонада standby instance жасай бастайды. Бұл процесс 10 минутқа дейін созылуы мүмкін. Кейінірек қайтып келіп, парақшаны жаңартып, өзгерістерді көре аласыз. Маңыздысы — біз енді дерекқорды да жоғары қолжетімді етіп жасадық. Біз зертханалық жұмыстың соңғы тапсырмасына жеттік — бұл опционалды тапсырма №2. Біз мұнда NAT gateway-дің жоғары қолжетімділігін баптаймыз. NAT gateway дегеніміз не? Бұл — public subnet-те орналасқан ресурс, ол private subnet-тегі ресурстарға интернетке шығу мүмкіндігін береді. Алайда интернеттен private subnet-тегі ресурстарға қол жеткізу мүмкін емес. Енді біз NAT gateway-дің жоғары қолжетімділігін баптап, көршілес availability зонада дәл сондай NAT gateway жасаймыз. Ол үшін VPC сервисіне өту қажет. Содан кейін сол жақтағы навигациялық мәзірден NAT gateways бөлімін таңдаймыз. Мұнда біз жаңа NAT gateway жасаймыз, ол үшін экранның оң жақ жоғарғы бөлігіндегі Create NAT gateway батырмасын басамыз. Жаңа ресурс үшін деректерді енгізу парақшасы ашылады: Subnet ретінде Public Subnet 2 таңдаймыз, одан кейін Allocate Elastic IP батырмасын басамыз және төменгі оң жақтағы Create NAT gateway батырмасын басамыз. Жаңа NAT gateway құрылғаннан кейін, енді private subnet 2 үшін Route table баптауымыз қажет. Жаңа route table жасаймыз және трафикті жаңа NAT gateway-ге бағыттаймыз. Ол үшін сол жақтағы навигациялық мәзірден Route tables пунктін таңдаймыз. Барлық route table-дер парақшасы ашылады, мұнда экранның оң жақ жоғарғы бөлігіндегі Create route table батырмасын басамыз. Жаңа ресурс үшін деректерді енгізу парақшасы ашылады: Name ретінде Private Route Table 2, VPC ретінде Lab VPC көрсетеміз және төменгі жағындағы Create route table батырмасын басамыз. Route table таңдасақ және Routes парақшасына өтсек, онда тек жергілікті трафикке рұқсат беретін бір ғана route бар екенін көреміз. Енді екінші route қосу қажет, осылайша private subnet-тегі ресурстар интернетке шығу мүмкіндігіне ие болады. Ол үшін Edit routes батырмасын басып, жаңа парақша ашылады. Онда Add route батырмасын басамыз, жаңа route үшін жол қосылады. Destination ретінде барлық нөлдерден тұратын CIDR блок көрсетеміз (интернет), ал Target ретінде NAT gateway таңдаймыз. Мұнда абай болу керек, нақты жаңа жасалған NAT gateway-ді таңдау қажет. Қателеспеу үшін басқа парақшада NAT gateways тізімін ашып қойсаңыз болады. Төменгі оң жақта Save changes батырмасын басып, өзгерістерді сақтаймыз. Енді жаңа route table-ді private subnet-пен байланыстыру қажет. Subnet associations парақшасына өтіп, Edit subnet associations батырмасын басып, private subnet 2-ні таңдаймыз. Содан кейін төменгі оң жақтағы Save associations батырмасын басу қажет. Осы әрекет арқылы біз NAT gateway-ді де жоғары қолжетімді етіп жасадық. Private subnet 2-де орналасқан барлық ресурстар өздерінің availability зонасындағы NAT gateway арқылы интернетке шыға алады. Сол себепті көршілес availability зонадағы ақаулар осы зонадағы ресурстарға әсер етпейді және олар тәуелсіз жұмыс істейді. Осылайша біз зертханалық жұмыстың негізгі бөлігін аяқтадық және енді автобағалау процесін бастауымыз қажет. Ол үшін зертханалық жұмыстың басты парақшасына оралып, Submit батырмасын басамыз, содан кейін бұл әрекетті растаймыз. Біршама уақыттан кейін автобағалау скрипті іске қосылып, нәтижелер көрсетіледі. Егер бұл орын алмаса, онда Grades батырмасын басып, жинаған балдарыңызды көре аласыз. Егер сіз жеткіліксіз балл жинасаңыз, кез келген тапсырмаға қайта оралып, тиісті өзгерістер енгізіп, AWS Management Console арқылы қайтадан автобағалауды іске қоса аласыз. Нәтиже сізді қанағаттандырған соң және қажетті балл жинаған кезде барлық жүйелерден дұрыс шығу қажет. Бұл ең алдымен AWS Management Console-ге қатысты, сондай-ақ зертханалық жұмыс сессиясын дұрыс аяқтау керек. Зертханалық жұмыстың басты парақшасында End lab батырмасын басып, бұл әрекетті растаңыз. Осылайша біз зертханалық жұмысымызды аяқтадық. Назар аударғандарыңызға рахмет, келесі белсенділіктерде кездескенше!
