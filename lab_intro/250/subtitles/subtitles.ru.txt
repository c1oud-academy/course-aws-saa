Мы с вами начинаем второе задание в рамках нашей лабораторной работы и будем создавать Application Load Balancer. Для того, чтобы сделать ваше приложение высокодоступным рекомендуется распределять ресурсы на несколько availability зон, как минимум две availability зоны. Идея ее в том, что каждая availability зона - это один или несколько отдельно стоящих физических дата-центров. И когда вы распределяете нагрузку на несколько availability зон, запросы уходят абсолютно физически в другие независящие друг от друга дата-центры. И в случае если будут проблемы на стороне одной из availability зон, то ваши пользователи не заметят эту проблему, так как вся нагрузка переляжет на работающую availability зону. После того как проблемная availability зона вновь восстановится, ваши нагрузки будут распределены равномерно по всем вашим availability зонам. Вероятность того, что несколько availability зон сразу станут недоступными маловероятна, поэтому это является самым первым и основным шагом, чтобы сделать ваше приложение высокодоступными. Best practice реализации высокодоступности внутри AWS является сервис Elastic Load Balancing, то есть ELB. Есть три разновидности, которые мы подробно разобрали на лекции, это ALB, Application Load Balancer, NLB, Network Load Balancer и Classic Load Balancer, который мы сейчас не можем создать, так как оно существует для поддержания обратной совместимости. Окей, дальше. Теперь как только запрос доходит до Application Load Balancer, он направляет HTTP трафик на application сервера. Application сервера работает в связке с базой данных, поэтому обращается к базе данных, отправляет трафик нашей базе данных и здесь аналогично инстанс базы данных, он тоже привязан к некоторой security группе. Если она разрешает входящий трафик, то запрос будет обработан базой данных, если нет, то база данных этого запроса не увидит. Первая security группа - это security группа load balancer, мы ее уже подготовили так как нужно во время создания нашего load balancer. Если вы помните, оно разрешает любой входящий HTTP и HTTPS трафик. Далее мы настраивали load balancer, он направляет весь свой трафик target группе. А Auto Scaling group соответственно при создании новых EC2 инстансов регистрирует инстанс в этой же target группе. Следующая security группа - это Application security group. Оно требует некоторых изменений, нам необходимо разрешать трафик только из нашего load balancer. Для этого необходимо в сервисе EC2 воспользоваться навигационным меню слева и выбрать пункт Security groups. Здесь необходимо выбрать security группу Inventory-Apps, в нижней части экрана отобразятся несколько вкладок. Нас интересует вкладка Inbound rules, здесь вы видите, что он пустой, поэтому нам необходимо добавить rule, который разрешает HTTP трафик от load balancer. Почему мы не включаем HTTPS трафик, так это то, что load balancer и наши application сервера находятся в одной инфраструктуре, поэтому здесь между ними создавать защищенный трафик нет необходимости. Более того HTTPS трафик требует больше вычислительных мощностей и работает медленнее, поэтому рекомендуется получать на стороне load balancer трафик HTTP и HTTPS. Но трафик между load balancer и application серверами отправлять только через HTTP, это является best practice. Для этого необходимо нажать на кнопку Edit inbound rules. Мы добавляем новый rule, выбираем как Type - HTTP, как Source указываем Custom и в соответствующем поле начинаем вводить sg. Здесь отобразится список всех security group, нам необходимо выбрать security group у нашего load balancer, называется Inventory-LB. Как Description давайте укажем Traffic from load balancer, чтобы потом легче вспомнить для чего этот rule создавался. В нижней правой части экрана необходимо будет нажать кнопку Save rules. На этом мы настроили нашу вторую security группу и мы можем принимать трафик на наши веб-сервера только от load balancer. В этот rule также входят автоматические health checks от load balancer, которые проверяют доступны ли веб-сервера или нет. У нас осталась последняя security группа - это security группа баз данных. На текущий момент у этой security группы есть один единственный inbound traffic, он разрешает traffic по порту 3306 для любого IP адреса из нашего VPC. Это хороший rule, но мы можем его сделать еще лучше, поэтому мы выбираем из списка security групп, security групп Inventory-DB. Далее открываем вкладку Inbound rules и нажимаем на кнопку Edit inbound rules. Теперь нам необходимо удалить существующий rule и вместо него создать новый. Для этого нажимаем на кнопку Add rule, далее как Type rule выбираем MYSQL/Aurora, он автоматически подставит порт 3306. Далее как Source указываем Custom и в следующем поле начинаем вводить sg, он отобразит список существующих security групп. Здесь необходимо будет выбрать Inventory-App, как Description давайте укажем Traffic from application servers, чтобы мы сразу вспомнили для чего мы создавали этот rule. В нижней правой части экрана нажимаем на Save rules, отлично. Теперь мы обновили все наши security группы и сейчас у нас трехуровневая защита, то есть каждый последующий уровень защищен и может принимать трафик только от ожидаемых ресурсов предыдущего слоя ресурсов. Самый первый слой - это у нас интернет, он обращается к нашему load balancer, до load balancer он доходит только в том случае, если проходит security группу самого load balancer. Далее, load balancer балансирует трафик на наши application сервера, опять же до application серверов доходит трафик только в том случае, если он проходит security группу application серверов, а соответственно эта security группа она разрешает трафик только от load balancer, любой другой трафик до application серверов не дойдет. Далее, уже application сервера по необходимости в зависимости от логики работы программы, будут обращаться к базе данных. На стороне базы данных у нас тоже есть security группа, она соответственно разрешает трафик только от ожидаемых ресурсов, а именно от application серверов. Мы с вами добрались до пятого задания лабораторной работы и сейчас будем тестировать наше приложение. Для этого первым делом необходимо перейти к target группам, то есть в навигационном меню слева воспользуемся пунктом Target groups. Далее из списка выбираем нашу target группу, это Inventory-App. Как только откроется основная страница ресурса, в нижней части мы увидим несколько вкладок. Нас интересует вкладка Targets, обратите внимание, что у нас будут два зарегистрированных таргета, оба должны быть в состоянии Healthy. Также вы увидите, что наши таргеты распределены по двум availability зонам. Отлично, теперь мы можем воспользоваться навигационным меню слева и выбрать пункт Load balancers. Далее мы выбираем наш load balancer Inventory-LB и в деталях этого ресурса мы можем скопировать DNS name, это URL-адрес нашего load balancer. Давайте откроем ее в новой вкладке браузера и вы увидите на странице instance ID и availability зоны. Попробуйте несколько раз обновить страницу, либо эту же ссылку открыть в другом браузере и тогда вы заметите, что instance ID и availability зона меняется. Это значит то, что наши запросы по очереди попадают к инстансам из двух availability зон. Мы с вами добрались до шестого задания нашей лабораторной работы и сейчас будем тестировать высокую доступность, которую настроили. Для того чтобы ее протестировать мы будем терминетить один из EC2 инстансов и смотреть что дальше будет происходить. В первую очередь нам необходимо скопировать URL-адрес load balancer и открыть ее в новой вкладке браузера. Как только откроется страница необходимо запомнить какой instance ID и из какой availability зоны обработал наш запрос. Нам необходимо оставить эту вкладку открытой и вернуться на страницу с AWS Management Console. Там необходимо перейти в сервис EC2, открыть список Instances и найти тот конкретный инстанс с названием Inventory-App и который находится в нужной availability зоне. Далее необходимо будет выбрать этот инстанс в верхней правой части, нажать на кнопку Instance state, выпадающем в списке выбрать Terminate instance и подтвердить отключение. Теперь начинается самое интересное, нам необходимо вернуться на вкладку с URL-адресом load balancer и периодически обновлять страницу. Мы будем получать ошибку, это нормально, так как EC2 инстанс недоступен, он не может обрабатывать запросы, а load balancer пока еще не пометил нездоровым этот конкретный инстанс. Пройдет некоторое время, в районе минуты может быть чуть больше и load balancer пометит наш отключенный инстанс как нездоровый и перенаправит весь трафик на второй инстанс. Тогда вы сможете открыть страницу веб-приложения, но при этом ID инстанса и availability зона уже будет другая. Теперь, как только вы переключитесь, что бы вы не делали, обновляйте страницу любое количество раз, либо открываете в инкогнито режиме, либо переключаете браузер, вы всегда будете получать запросы из конкретного инстанса, с конкретной availability зоны. До того момента, как не произойдет восстановление второго инстанса, он автоматически поднимется на второй availability зоне и как только оно будет готово и подключено к load balancer, трафик уже будет распределяться равномерно между двумя EC2 инстансами. И вы начнете замечать, что ваши запросы попеременно обрабатываются инстансами из разных availability зон. Мы с вами успешно прошлись по всем основным заданиям лабораторной работы. Также предлагается два опциональных задания, они не оцениваются, но вы по желанию можете их выполнить. Первое опциональное задание предлагает нам настроить высокую доступность нашей базы данных. Если мы посмотрим на диаграмму нашей IT-инфраструктуры, то почти все ресурсы распределены по двум availability зонам и являются высокодоступными. Но база данных в единственном числе находится в одной из availability зон и в случае возникновения проблем с целой availability зоной либо с конкретным этим инстансом, то вся наша высокая доступность других частей нашей IT-инфраструктуры не поможет. Поэтому нам необходимо исключить это слабое звено и сделать нашу базу данных также высокодоступный. Сервис Amazon RDS позволяет это настроить. Итак, давайте пройдемся по шагам, чтобы посмотреть как это делается. В первую очередь нам необходимо воспользоваться строкой поиска сервисов, начать вводить RDS и перейти на соответствующий сервис. Откроется главная страница этого сервиса, здесь необходимо воспользоваться навигационным меню слева и выбрать пункт Databases. Отобразится список существующих баз данных в этом AWS аккаунте, скорее всего будет один-единственный инстанс, это наша база данных с названием Inventory-DB. Давайте откроем этот ресурс и в верхней правой части нажмем на кнопку Modify. Откроется страница редактирования ресурса баз данных. Здесь необходимо будет проскроллить до секции Availability and durability. Далее в подсекции Multi-AZ deployment необходимо будет выбрать Create a standby instance. Что такое standby instance? Это инстанс базы данных, работающих в пассивном режиме в другой availability зоне, тогда как основной инстанс является активным и обрабатывает трафик. Как только происходит какая-то проблема либо со всей availability зоной, либо конкретно с инстансом баз данных, которая основная, происходит автоматическое переключение трафика на standby instance, он полностью переключается, при этом адрес базы данных не меняется. Для ваших приложений, для веб-приложений это изменение оно прозрачное. Таким образом достигается высокая доступность базы данных. Размер standby instance может быть таким же, либо чуть меньше. Это можно настроить, мы в рамках нашей лабораторной работы укажем размер db.t3.small и как выделяемое дисковое пространство для данных укажем 10 гигабайтов, это поле Allocated storage. Теперь нам необходимо проскроллить до конца страницы и нажать на кнопку Continue. Далее будет предложено внести изменения либо по расписанию, либо сразу. В рамках этой лабораторной работы мы будем вносить изменения сразу, после этого инстанс перейдет в состояние Modifying и он будет создавать standby instance в другой availability зоне. Это может занять до 10 минут, поэтому вы можете вернуться через некоторое время и обновить страницу, посмотрите какие изменения произошли. Но идея в том, что мы сделали нашу базу данных также высокодоступной. Мы с вами добрались до самого последнего задания этой лабораторной работы, это опциональное задание номер 2. Здесь мы будем настраивать высокую доступность нашего NAT gateway. Что такое NAT gateway? Это тот ресурс, который находится в public subnet и предоставляет доступ в интернет ресурсам из private subnet. Но при этом из интернета до ресурсов в private subnet добраться невозможно. Давайте теперь настроим высокую доступность нашего NAT gateway и создадим такой же NAT gateway в соседней availability зоне. Для этого нам необходимо перейти в сервис VPC. Как только мы это сделаем, необходимо воспользоваться навигационным меню слева и выбрать пункт NAT gateways. Здесь мы будем создавать новый NAT gateway, поэтому необходимо нажать на кнопку Create NAT gateway в верхней правой части экрана. Откроется страница ввода данных нового ресурса, как Subnet укажем Public Subnet 2, далее нажимаем на кнопку Allocate Elastic IP и в нижней правой части экрана нажимаем Create NAT gateway. Как только мы создадим новый NAT gateway, нам теперь необходимо настроить Route table для private sabnet 2. Мы создадим новый route table и перенаправим трафик на наш новый NAT gateway. Для этого необходимо воспользоваться навигационным меню слева и выбрать пункт Route tables. Откроется страница со всеми route tables, здесь необходимо будет нажать на кнопку Create route table в верхней правой части экрана. Откроется страница для ввода данных нового ресурса, как Name укажем Private Route Table 2, далее как VPC укажем Lab VPC и нажмем на кнопку Create route table в нижней части экрана. Если мы выберем наш route table и перейдем на вкладку Routes, мы увидим, что есть один единственный route, который разрешает локальный трафик внутри нашего VPC. Теперь нам необходимо добавить второй route, чтобы ресурсы из private subnet могли выходить в интернет, используя новый NAT gateway. Для этого нам необходимо будет нажать на кнопку Edit routes и откроется новая страница. Там необходимо будет нажать на кнопку Add route, добавится новая строчка для нового route. Здесь как Destination указываем CIDR блок со всеми нулями, то есть интернет, далее как Target указываем NAT gateway. Здесь необходимо быть аккуратным и выбрать новый созданный NAT gateway, для этого вы можете в другой вкладке открыть список NAT gateways, чтобы не ошибиться. В нижней правой части нажимаем на кнопку Save changes, чтобы сохранить изменения. Теперь новый route table необходимо привязать к нашему private subnet. Для этого переходим на вкладку Subnet associations, нажимаем на кнопку Edit subnet associations и выбираем private subnet 2. Далее необходимо будет нажать на кнопку Save associations в нижней правой части экрана. Как только мы это сделаем, мы сделаем наш ресурс NAT gateway также высокодоступным. Все ресурсы находящиеся в private subnet 2 будут выходить в интернет, используя NAT gateway из той же availability зоны. Таким образом проблемы в соседней availability зоне никак не отразятся на ресурсах в текущей availability зоне и они работают независимо друг от друга.
