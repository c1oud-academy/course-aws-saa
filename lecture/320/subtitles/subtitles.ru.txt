А во второй части нашей сегодняшней сессии мы познакомимся с сервисом AWS Step Functions, который позволяет оркестрировать микросервисы. Amazon API Gateway это полностью managed решения от AWS, которое позволяет нам создавать, публиковать, обслуживать, мониторить и настраивать безопасность наших API любых масштабов. Используя API Gateway мы можем настроить наши API на базе RESTful либо WebSockets. Сам API Gateway настраивается довольно просто, интегрируется с множеством AWS сервисов, это Lambda, EC2 и так далее. API Gateway может обслуживать сотни тысяч параллельных API вызовов в секунду. Помимо этого API Gateway мы можем настроить контроль трафика, авторизацию, контроль доступа, мониторинг и управление versions наших API. За использование сервиса API Gateway мы ничего не платим наперед, нет никаких стартовых вложений, мы оплачиваем только за то, что мы используем. А оплачиваем мы за объемы трафика, проходящего через API Gateway. Если трафика нет, то мы либо оплачиваем совсем ничего, либо оплачиваем минимальную сумму. При этом наша инфраструктура будет полностью готова принять большой объем внезапного трафика. Если мы говорим про безопасность, то Amazon API Gateway поддерживает ряд подходов, которые могут обезопасить наши API. Первое – это возможность настройки авторизации, это может быть либо кастомная лямбда, либо нативное решение от API Gateway. Далее мы можем настроить policy так, чтобы только выбранные внутренние ресурсы в нашей инфраструктуре могли работать с API Gateway. Если мы говорим про вызовы, то мы можем также настроить Throttling логику, если мы знаем, что выбранный API не может быть вызван более X количества раз в секунду, то наложив на него ограничения, мы сократим спам вызовы нашего API. И последний продвинутый подход – это подключить к API Gateway сервис AWS WAF для того, чтобы быть готовым к DDoS-атакам. На этом слайде вы видите пример популярной архитектуры, когда используется Amazon API Gateway. У нас в самом начале есть наши пользователи, которые через интернет обращаются к нашему приложению. Они попадают на CloudFront, далее эти вызовы перенаправляются на API Gateway. API Gateway самостоятельно логирует информацию о трафике в Amazon CloudWatch и можно настроить на стороне API Gateway логику кэширования. Далее весь этот трафик направляется на разнообразие ресурсов внутри нашей инфраструктуры, это Lambda functions, EC2 инстансы, это могут быть ресурсы внутри VPC, либо отдельно стоящие AWS сервисы. На этом же слайде мы видим пример микросервисной архитектуры. У нас есть наши пользователи, обращаются через интернет в наше приложение и эти вызовы попадают в API Gateway. API Gateway достаточно тесно может быть интегрирован с AWS Lambda, то есть для построения микросервисных приложений и бессерверных архитектур. Запросы от API Gateway попадают в AWS Lambda, Lambda при необходимости может работать с DynamoDB, либо с любой другой базой данных и вернуть ответ пользователям через API Gateway. И, пожалуй, последний пример архитектуры, которой используется API Gateway, это backend мобильного приложения, при этом вся инфраструктура бессерверная. Есть наши пользователи, они через приложение делают вызовы в API Gateway. Далее API Gateway через кастомную лямбда-функцию и с помощью Amazon Cognito, либо AWS STS авторизует этот запрос и, соответственно, пользователи вашего приложения. Далее вступает основная логика приложения, все авторизованные вызовы попадают на нашу Lambda. Эта лямбда далее уже в зависимости от запроса и логики работы вашего приложения может работать с данными из DynamoDB, S3, ElastiCache, либо базы данных RDS. Мы с вами начинаем заключительную часть нашей сегодняшней сессии и здесь познакомимся с сервисом AWS Step Functions для оркестрации наших микросервисов. Представим, что у нас есть некоторое приложение, в рамках этого приложения на уровне бессерверной архитектуры запускается множество лямбд. Лямбды в зависимости от процесса имеют определенный порядок и каждая лямбда запускает одну либо несколько других лямбд для продолжения процесса. Вы видите на диаграмме с увеличением количества лямбд и усложнение логики, это может сильно запутать и усложнить разработку. На стороне AWS есть готовое решение, это сервис AWS Step Functions, который позволяет нам координировать наши микросервисы между собой, оборачивая это все в визуальный workflow. Мы создаем workflow, используя специальный язык и элементы, созданные командой AWS. Далее можно будет в удобном интерфейсе визуально видеть, как отрабатывает наше workflow. Мы можем наблюдать на каком узле произошла ошибка, почему она произошла и посмотреть больше деталей по текущему либо предыдущим узлам этого workflow. Используя специальный язык описания workflow мы можем производить различные действия. На этом слайде вы видите основные примеры, мы можем настроить последовательность task. Task это задание, а каждое задание это одна лямбда. Мы можем также настроить в зависимости от условия запуск определенной лямбды, либо можем настроить параллельный запуск нескольких лямбд, в результате которого запускается следующая лямбда последовательно. Можем также настроить Retry логику, либо try-catch логику, которая в зависимости от ошибки либо успешности выполнения первого задания запускала ту или иную лямбду. Каждый узел нашего workflow называется state, а набор связанных между собой состояний называется state machine. Давайте теперь с вами разберем пример простейшей state machine. Представим, что у нас есть мобильное приложение, в мобильное приложение вы можете загружать фотографии. Эти фотографии сохраняются в приложении, также для каждой фотографии генерируется мини-копия этой фотографии и делается попытка распознавания того, что изображено на картинке. И эти теги также как мета-данные привязываются к нашему изображению. Для этого мобильного приложения state machine могла бы выглядеть следующим образом. Как только изображение попало в S3 bucket, генерируется автоматический event, который триггерит нашу state machine. State machine запускает task, первая task это лямбда, которая извлекает мета-данные нашего изображения, после чего происходит проверка типа этого изображения. Если этот тип изображения не поддерживается, то оно падает с ошибкой. Далее можно настроить отправку уведомлений, либо отправку сообщений на прямую пользователю о том, чтобы пользователь загрузил другое изображение. Если же тип изображения поддерживается, то запускаются параллельные задания. Первое задание это генерация Thumbnail, то есть миниатюрная копия этого изображения, а второе параллельное задание это Rekognition. Мы передаем наше изображение специальному сервису, который пытается распознать объекты внутри нашего изображения. Если что-то находится, то следующая лямбда эти теги привязывает к нашему изображению, после чего state machine завершает свою работу. Давайте теперь разберем, какие типы узлов бывают в state machine. Первое это Task, с ней мы уже успели познакомиться, Task запускает одну из лямбд. Далее идет Choice, это в зависимости от входящих данных происходит переход к одному, либо другому направлению внутри state machine. Аналогом в программировании является и EFails block. Третий тип это Fail и четвертый Succeed, они связаны между собой. Мы можем в различные ветви state machine добавлять как конечную точку, либо Fail, либо Succeed в зависимости от логики вашей state machine. Следующий тип узла это Pass, сам он по себе не производит никакую работу, но он может входящую структуру трансформировать и передать следующему узлу в измененном виде. Далее у нас идет тип Wait, который также не производит никакой работы, но он может задержать на указанное количество секунд отработку state machine. Это очень удобно, так как мы можем встроить в state machine ожидание пока другая ветка, либо другая асинхронная задача успеет отработать до выполнения следующего узла state machine. Еще один тип узла с которым мы успели познакомиться это Parallel, идея ее в том, что мы можем запускать целые ветки state machine, либо единичные задания независимо друг от друга, что может быть удобным. И самый последний из основных типов узлов это Map. Идея ее в том, что мы можем передать набор одинаковых элементов для отработки каждого из них циклично, то есть прямым аналогом Map узла в языке программирования является цикл. На этом слайде вы с левой стороны видите пример JSON, которая описывает state machine, мы подробнее ее разбирать не будем в рамках нашей сессии. А с правой стороны мы видим визуализацию этой state machine в сервисе AWS Step Functions. Давайте разберем один из примеров архитектуры, где используется AWS Step Functions. Самый популярный пример - это подготовка видео для трансляции в интернете. Мы загружаем исходное видео в S3 bucket, далее S3 bucket проходит через workflow. Внутри workflow содержится Step Functions и дополнительные сервисы, которые приводят наше видео в необходимый формат. После чего, после завершения workflow результаты передаются в соответствующие сервисы, это либо S3, либо Elemental Media Package и с использованием CloudFront можно будет транслировать ваше видео вашим пользователям.
