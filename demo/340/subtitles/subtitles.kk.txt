Бүгінгі сессияда біз тек ресми AWS емтиханында ғана емес, сонымен қатар бұлт инженері ретінде шынайы өмірде жиі кездесетін сценарийлерді қарастырамыз. Онда, бастайық. Бұл демо үшін ақпарат көзі — tutorialsdojo.com сайтындағы AWS Certified Solutions Architect Associate емтиханына арналған парақша. Бұл — емтиханды әртүрлі қырынан қарастыратын ауқымды парақша. Бізді қызықтыратыны — жиі кездесетін сценарийлерге арналған блок. Бұл парақшаға шығу үшін іздеу жүйесіне “bonso aws saa common scenarios” деп жазуға болады. Барлық сценарийлер төрт доменге бөлінген. Бұл — AWS SAA емтиханында кездесетін барлық домендер. Бірінші домен — AWS бұлтында қауіпсіз архитектураларды құру. Бірінші сценарий — бізде шифрланбаған EBS snapshot-тар бар, оларды қалпына келтіріп, шифрланған етуіміз қажет. Бұны жасау үшін алдымен snapshot көшірмесін жасау керек. Қалпына келтіру кезінде шифрлау кілтін көрсетіп, шифрланған түрде жасаймыз. Келесі сценарий — белгілі бір IP-адрестен көп сұраныс келіп түсуде, біз осы IP үшін сұраныстар санын шектеуіміз керек. Мұны жасау үшін API Gateway-ге AWS WAF қосып, сол жерде rate-based rule жасап, лимит орнату қажет. Келесі сценарий — бізде әртүрлі дереккөздер жүктейтін объектілері бар S3 bucket бар. Bucket иесі осы bucket ішіндегі барлық объектілерге толық қолжетімділік алуы қажет. Ол үшін bucket policy құру қажет. Bucket policy пайдаланушылардан объект ACL-ін bucket-owner-full-control мәніне орнатуды талап етеді. Келесі сценарий — біз S3 bucket ішіндегі объектілерді кездейсоқ жою немесе қайта жазудан қорғауымыз керек. Бұған қол жеткізу үшін versioning функциясын және объектіні жою кезінде MFA растауын қосу қажет. Келесі сценарий — бұл корпоративтік ортаға қатысты. Әр қызметкерде логин мен пароль бар, осы деректермен ол ішкі инфрақұрылымдағы ресурстарға қол жеткізе алады. Егер осы деректер арқылы қызметкерге AWS ресурстарына да қолжетімділік беру қажет болса ше? Бұл үшін Microsoft AD-дегі Federation Service және SAML 2.0-базаланған федерацияны баптау қажет. Келесі сценарий — EBS қатқыл дискілерінде құпия ақпаратты қорғау қажет. Шешімі — EBS дискілерін шифрлау. Келесі сценарий — S3 Bucket ішіндегі деректерді тек сақтау кезінде ғана емес, тасымалдау кезінде де қорғау қажет. Бұл үшін Server-Side Encryption немесе Client-Side Encryption қосу керек. Келесі сценарий — бірнеше домен арқылы SSL Traffic қосу арқылы веб-қосымшаны қорғау қажет. Шешімі — AWS Certificate Manager сервисін пайдалану және SSL сертификатын генерациялау. Содан кейін бұл сертификатты CloudFront Distribution-ға тіркеп, Server Name Indication функциясын белсендіру қажет. Келесі сценарий — Gateway Endpoint пайдаланып, бөлінген S3 Bucket-ке қол жеткізуді қамтамасыз ету. Бұл үшін S3 Bucket үшін Endpoint Policy жасау керек. Келесі сценарий — кез келген AWS сервистерінің конфигурацияларындағы өзгерістерді қатаң бақылау қажет. Бұл үшін AWS Config сервисінде rule жасау керек. Сонда сіз қандай сервистер талаптарға сай, ал қайсысы сай емес екенін көріп, сәйкес түзетулер енгізе аласыз. Келесі сценарий — AWS ресурстарына уақытша қол жеткізу беру қажет. Бұл үшін AWS Security Token Service (STS) қолдану қажет. Келесі сценарий — дерекқор credentials, API кілттерін және басқа да құпияларды үнемі жаңартып, қауіпсіз сақтау керек. Бұл міндетті орындау үшін қай сервисті қолдануға болады? Шешім — AWS Secrets Manager сервисін пайдалану. Бұл сервис арқылы credentials-ті автоматты түрде айналдыруды (rotation) қосуға болады. Енді екінші доменге қатысты жиі кездесетін сценарийлерге көшеміз. Екінші домен — сенімді және икемді архитектураларды құру. Сценарий: Бізге RDS инстансынан басқа AWS аймағындағы тағы бір инстансқа асинхронды түрде деректер репликациясын орнату қажет. Шешімі — read репликаны жасау қажет. Келесі сценарий: Бізге жиі сұранысқа ие деректерге параллель қолжетімділік ұсынатын файлдық жүйе қажет. Шешімі — Amazon FSx for Lustre сервисін пайдалану. Келесі сценарий: дерекқор деректері көрші availability зонасындағы инстансқа синхронды түрде репликациялануы тиіс. Негізгі инстанспен мәселе туындаса, автоматты түрде failover болып, трафик екінші инстансқа ауысуы қажет. Шешімі — RDS инстансында Multi-AZ deployment функциясын қосу қажет. Сценарий: Бізге сирек қолданылатын немесе мүлде қолданылмайтын "салқын" деректерді сақтау қажет. Шешім — Amazon S3 Glacier сервисін пайдалану. Сценарий: Реляциялық дерекқор үшін disaster recovery жоспары қажет. RPO — 1 секунд, ал RTO — 1 минуттан аз болуға тиіс. Шешім — Amazon Aurora-ның Global Database функциясын қолдану ұсынылады. Сценарий: Бізге дерекқор метрикаларын бақылау қажет. Белгілі бір шектен асқан жағдайда — пошта арқылы хабарлама жіберу керек. Шешім — CloudWatch alarm орнатып, оған SNS topic байлау. Сонымен қатар, осы SNS topic-ке жазылымды растау қажет. Сценарий: Статикалық веб-сайт үшін DNS failover орнату қажет. Бұл қажет болуы мүмкін мысалдардың бірі, егер бізде веб-қосымша бар болса және ол қандай да бір себептермен жұмысын тоқтатады. Егер пайдаланушылар қалпына келтіру жұмыстары жүріп жатқаны туралы ақпараты бар статикалық веб-сайтқа қайта бағытталса, олар не болып жатқанын түсінеді және қолданба сақтық көшірмесін жасап, іске қосылғанда, біраз уақыттан кейін жұмысын жалғастыра алады. Егер сайт ашылуды тоқтатса, пайдаланушылар не болып жатқанын түсінбейді және кейбір пайдаланушыларды жоғалтуыңыз мүмкін. DNS failover баптау үшін Route 53 жағында failover опциясы үшін қажетті мәндерді енгізу қажет. Бұл жағдайда Destination статикалық веб-сайты немесе CloudFront Distribution бар S3 bucket болады. Сценарий: Бізге EBS дискілерінің автоматты backup-н орнату қажет. Шешім — Amazon Data Lifecycle Manager сервисін қолдану. Сценарий: EC2 инстанстарындағы swap space-ті бақылау қажет. Шешім — CloudWatch agent орнатып, SwapUtilization метрикасын бақылау. Сценарий: Amazon Aurora-ның backup-н 90 күнге дейін сақтау policy орнату керек. Шешім — AWS Backup сервисін қолдану. Біз үшінші доменге жеттік. Үшінші домен — жоғары тиімді архитектураларды құрудағы жиі сценарийлер. Сценарий: Fanout messaging іске асыру қажет. Яғни, бір хабарламаны бірнеше алушыға жіберу. Шешім — SNS topic құру. Қажет болса, хабарлама фильтрі үшін policy теңшей аламыз және SNS topic-ке SQS кезектерінің қажетті санын жаза аламыз. Сценарий: Read-реплика лагі 1 секундтан аз болатын дерекқор қажет. Шешім — Amazon Aurora with cross-region replica пайдалану. Сценарий: Онлайн-ойын бар, серверлерге мыңдаған клиент бір уақытта қосылады. UDP протоколын қолдайтын Elastic Load Balancer қолдану қажет. Шешім ретінде Network Load Balancer қолдану ұсынылады. Бұл Elastic Load Balancer-дің ішкі түрі, ол TCP және UDP протоколдарын қолдайды. Сценарий бойынша бізге EC2 инстансымыздағы оперативті жад пен қатқыл дискінің қолданылған көлемін бақылау қажет. Оны бақылау үшін EC2 инстансымызға CloudWatch Agent орнату қажет. Сценарий бойынша бізде S3 бакетінде сақталған көлемді CSV файл бар. Бізге осы файлдан белгілі бір деректерді шығару қажет. Бұл тапсырманы шешу үшін S3 Select функционалын қолдану ұсынылады, ол сұраныс жазып, белгілі бір S3 бакеттегі файлдан қажетті деректерді алуға мүмкіндік береді. Сценарий бойынша бізге көлемі 1 терабайт болатын үлкен файлды S3 бакетіне жүктеу қажет. Оны орындау үшін Amazon S3 сервисінің Multipart Upload функционалын қолдану ұсынылады. Бұл үлкен объектілерді бөліктерге бөліп, сол бөліктерді бөлек-бөлек жүктеуге мүмкіндік береді. Барлық бөліктер жүктелген соң, файл біртұтас етіп S3 бакетінде жинақталады. Бізге қолданбаның жұмысын оңтайландырып, latency-ді миллисекундтан микросекундқа дейін азайту қажет. Бұл жағдайда Amazon DynamoDB Accelerator немесе қысқаша DAX қолдану ұсынылады. Сценарий бойынша бізге EC2 инстансының метадеректерін шығару қажет, мысалы Instance ID, жалпыға ортақ кілттер және жалпыға ортақ IP-мекенжай. Мұны орындау үшін сіз EC2 инстансының ішінде белгілі бір мекенжайға жүгініп, барлық метадеректерді ала аласыз. Сценарий бойынша бізге пайдаланушылардың интернет-трафигін олардың орналасуына байланысты инфрақұрылым ресурстарына бағыттау қажет. Бұл жағдайда Route 53 сервисінің Geolocation Routing Policy қолдану ұсынылады. Сценарий бойынша бізге AWS ішінде ETL үшін толық managed шешім қажет. Жауап — AWS Glue сервисі. Сценарий бойынша бізге бірнеше петабайт көлеміндегі деректер витринасын басқаруға мүмкіндік беретін managed сервис қажет. Бұл жағдайда шешім — Amazon Redshift сервисі. Біз төртінші және соңғы доменге жеттік. Осы домен аясында бұлттағы шығындарды оңтайландыру тұрғысынан ең танымал сценарийлерді қарастырамыз. Сценарий бойынша бізге кіріс трафигіне байланысты қажетті ресурстарды автоматты түрде іске қосатын шешім қажет. Бұл жағдайда ASG ішіндегі Target Tracking Scaling қолдану ұсынылады. Сценарий бойынша қосымшаның деректері таспалы тасымалдағыштарда сақталады. Бұл деректерді 10 жылға дейін сақтауымыз қажет. Шешім ретінде AWS Storage Gateway сервисін қолданып, деректерді тікелей AWS S3 Glacier Deep Archive-қа жіберу ұсынылады. Бұл сирек немесе мүлдем сұралмайтын деректерді шығын тұрғысынан өте тиімді сақтайтын сервис. Келесі сценарий алдыңғысымен өте ұқсас. Мұнда бізге тарихи деректерді жергілікті инфрақұрылымнан AWS-ке ең аз шығынмен жеткізу ұсынылады. Бұл жағдайда AWS DataSync сервисін қолданып, Destination ретінде Amazon S3 Glacier Deep Archive көрсету ұсынылады. Сценарий бойынша бізге контентті бүкіл әлем бойынша ең аз кідіріссіз жеткізу қажет. Ол үшін деректерді S3 сервисінде сақтау қажет. Содан кейін CloudFront Distribution құрып, оның дереккөзі ретінде біздің S3 бакетті көрсету керек. Сценарий бойынша біздің қосымша екі EC2 инстансында жұмыс істейді және үш жыл бойы үздіксіз жұмыс істеуі тиіс. Жүктемелер болжамды және тұрақты болады. Бұлттағы шығындарды минималды болу үшін қандай шешім ұсына аласыз? Бұл жағдайда EC2 инстанстарын үш жылға Reserved Instance ретінде сатып алу ұсынылады. Сценарий бойынша бізге сирек сұралатын объектілерді сақтау үшін Cost Effective шешім қажет. Шешім ретінде Lifecycle Policy қолданып, белгілі бір уақыттан кейін объектілерді Standard-IA (Infrequent Access) классына көшіру ұсынылады. Сценарий бойынша бізге екі EC2 инстансы арасындағы деректерді беру шығындарын азайту қажет. Бұл жағдайда екі EC2 инстансын бір аймақта ұстау міндетті. Себебі Cross-Region деректерді беру қосымша шығынды талап етеді, ал бір аймақ ішінде ондай шығын болмайды. Сценарий бойынша бізге қосымшаның SSL сертификатын AWS бұлтына импорттау қажет. Шешім ретінде AWS Certificate Manager сервисін қолдану немесе SSL сертификатын AWS IAM сервисіне жүктеу ұсынылады. Біз бүгінгі демо-сессиямыздың соңына жеттік, AWS бұлтымен жұмыс істеудегі жиі кездесетін сценарийлерді талқыладық. Бұл білім сізге нақты AWS емтиханын тапсыру кезінде және бұлт инженері ретінде жұмыс барысында қажет болады. Назарларыңызға рахмет, жақын арада кездескенше!
