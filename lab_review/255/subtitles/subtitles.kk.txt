Қайырлы күн, құрметті студенттер! Мен сіздерді зертхана жұмысының талдау сессиясында көргеніме қуаныштымын. Бүгінгі зертхана жұмысының тақырыбы — AWS бұлтында автомасштабталатын және жоғары қолжетімді IT-инфрақұрылымды құру. Ендеше, бастайық. Біз бірінші тапсырманы бастаймыз. Осы тапсырма аясында уақытша AWS аккаунтында алдын ала қандай желілік ресурстар жасалғанын көру қажет. Одан кейін тест сұрақтарына жауап беру қажет. Біз AWS Management Console негізгі парақшасынан бастаймыз. Сондай-ақ сұрақтар тізімін аша аламыз. Ол үшін зертхана жұмысының басты парақшасына оралып, Show батырмасын басу керек. Ашылған қалқымалы терезеде Access the Multiple Choice Questions сілтемесі болады. Сол сілтемеге басқан кезде браузердің жаңа қойындысында алты сұрақ ашылады. Біз бірінші сұрақтан бастаймыз. Сұрақ келесідей. CafeSG атты Security Group аясында қандай порттар ашық? Security Group-тарға жету үшін алдымен VPC сервисін ашу керек. Сервистерді іздеу жолағын қолданып, VPC деп терейік. Бірінші сілтеме — бізге қажеті. Содан соң сол жақтағы навигациялық мәзірден Security Groups бөлімін таңдаймыз. Security Group-тар тізімі ашылады. Бізді CafeSG атаулы Security Group қызықтырады. Оны таңдайық. Экранның төменгі бөлігінде қосымша қойындылар ашылады. Бізді Inbound Rules қойындысы қызықтырады. Бізде интернеттен келетін 80-порттағы кіріс трафикке рұқсат беретін бір rule бар екенін көреміз. Сұрақтар парақшасына оралып, бірінші сұраққа жауап берейік. Дұрыс жауап — 80 порт. Submit батырмасын басып, артқа оралу қажет. Енді екінші сұрақты көрейік. Ол келесідей. Public Subnet 1 ішіндегі инстанстарға интернеттен қосыла аламыз ба? Мұны анықтау үшін сол жақ мәзірдегі Subnets тізімін ашу керек. Бізді Public Subnet 1 қызықтырады. Оны таңдайық. Сол сәтте экранның төменгі жағында қосымша қойындылар көрінеді. Route Table қойындысын таңдаймыз. Қандай routes бар екенін көрейік. Екінші route-ты қарасақ, Destination ретінде интернет CIDR блогы көрсетілген (барлығы нөлдер), ал Target — Internet Gateway. Бұл Public Subnet 1 шынымен де Public Subnet екенін және ондағы ресурстар интернеттен қолжетімді екенін білдіреді. Неліктен “қолжетімді болуы мүмкін”, себебі бізге Network ACL де тексеру қажет. Ол үшін Network ACL қойындысын ашып, қандай inbound rules бар екенін көреміз. Inbound rules ішінде екі default rule бар екенін көреміз және олар интернеттен келетін барлық кіріс трафикке рұқсат береді. Сұрақтар тізіміне оралып, сұраққа жауап береміз. Дұрыс жауап — бірінші жауап нұсқасы. Submit батырмасын басып, сұрақтар тізіміне ораламыз. Енді үшінші сұрақты қараймыз, ол келесідей. Private Subnet 1 ішіндегі инстанстар интернетке шыға ала ма? Ол үшін subnets тізімінен Private Subnet 1 таңдап, Route table ашу қажет. Route table ішінде екінші route бар екенін көреміз, онда Destination ретінде интернет CIDR блогы көрсетілген (нөлдер), ал Target — NAT gateway. Бұл Private subnet ішіндегі инстанстар интернетке шыға алатынын білдіреді, бірақ интернеттен бұл инстанстарға қосылу мүмкін емес, себебі NAT gateway қолданылады. Осылайша, сұрақтар тізіміне оралып, үшінші сұраққа Yes деп жауап береміз. Міндетті түрде Submit батырмасын басып, сұрақтар тізіміне қайта оралу керек. Төртінші сұрақ дәл осылай, бірақ ол Private Subnet 2-ге қатысты. Private Subnet 2-ні тексеріп, сұрақтар тізіміне ораламыз. Ол үшін subnets тізімінен Private Subnet 2 таңдап, Route table ашу қажет. Біз тек бір default route бар екенін көреміз, сондықтан төртінші сұрақтың жауабы — No, яғни Private Subnet 2 ішіндегі инстанстар интернетке шыға алмайды. Submit батырмасын басып, сұрақтар тізіміне қайта ораламыз. Келесі бесінші сұрақты қараймыз. Ол келесідей: интернеттен CafeWebAppServer инстансына қосыла аламыз ба? Мұны білу үшін инстанстар тізімін ашып, CafeWebAppServer атты инстансты таңдаймыз. Бұл серверде жалпыға ортақ IP-адрес бар екенін көреміз — жақсы. Енді экранның төменгі бөлігіндегі Security қойындысын таңдап, security топты көреміз. Келіп түсетін трафикке интернеттен 80-порт арқылы рұқсат беретін inbound rule бар екенін көреміз. Демек, ssh трафикке рұқсат жоқ. Енді Networking қойындысын қосымша тексеріп, бұл инстанс қай subnet-ке жататынын анықтайық. Ол Private Subnet 1-ге тиесілі екенін көреміз. Жақсы, енді бұл subnet-ті ашып, қандай routes бар екенін тексерейік. Private Subnet 1-ді таңдап, Route table қойындысын ашамыз. Destination ретінде Internet көрсетілген route бар, ал Target ретінде NAT gateway қолданылады. Біз NAT gateway — бұл интернетке шығуға көмектесетін, бірақ интернеттен қолжетімділікті бұғаттайтын арнайы ресурс екенін білеміз. Сондықтан бесінші сұрақтың дұрыс жауабы — No. Submit батырмасын басып, алтыншы сұраққа көшеміз. Алтыншы сұрақ келесідей. Уақытша AWS аккаунтында кастомды AMI жасалған және оны тауып, қалай аталатынын көру керек. Оны білу үшін сол жақтағы навигациялық мәзірден AMIs бөлімін таңдау қажет. Ашылған тізімде бір ғана AMI бар — оның атауы Cafe WebServer Image. Жарайды, сұрақтар тізіміне оралып, алтыншы сұраққа жауап береміз. Содан кейін Submit батырмасын басуды ұмытпаңыз. Осылайша, біз бірінші тапсырманы аяқтаймыз және екіншіге өте аламыз. Біз екінші тапсырманы бастаймыз. Бұл тапсырма аясында біз екінші availability зонасында NAT gateway құрамыз. Ол үшін сол жақтағы навигациялық мәзірден NAT gateways бөлімін таңдау қажет. Қазіргі уақытта бізде бір ғана NAT gateway бар. Оны таңдап, қай subnet ішінде жасалғанын көреміз. Ол үшін Details қойындысын ашып қараймыз — қазіргі NAT gateway Public Subnet 1 ішінде орналасқан. Жақсы, енді екінші NAT gateway-ді Public Subnet 2 ішінде құрамыз. NAT gateway жасау үшін экранның жоғарғы оң жақ бұрышындағы батырманы қолданамыз. NAT gateway жасау парақшасы ашылады. Мұнда Public Subnet 2 таңдау қажет. Содан кейін Allocate elastic IP батырмасын басу керек, ол автоматты түрде жасалып, NAT gateway-ге байланысады. Парақшаның соңына дейін жылжытайық және Create NAT gateway батырмасын басайық. Біз мұны жасағаннан кейін, бізді ресурс парақшасына қайта бағыттайды, сонымен қатар экранның жоғарғы жағында NAT gateway сәтті құрылғаны туралы жасыл фонда хабарлама көреміз. Енді бізге Route table-да кейбір өзгерістер енгізу қажет, қандай route table қажет екенін анықтау үшін, subnet мәліметтерін ашу керек. Сондықтан сол жақтағы навигациялық мәзірді қолданып, Subnets бөліміне өтеміз. Ашылған subnets тізімінен Private Subnet 2 таңдаймыз. Экранның төменгі бөлігіндегі қойындылардан Route table қойындысын таңдаймыз және осы жерде бізге қажет route table сілтемесі болады. Сол сілтемені басайық, сонда қажетті route table бойынша сүзгіден өткен route tables тізімі ашылады. Оны таңдайық және экранның төменгі бөлігінде Routes қойындысын ашайық. Бізде бір ғана әдепкі route барын көреміз, енді интернетке NAT gateway арқылы шығатын жаңа route жасауымыз қажет. Ол үшін Edit routes батырмасын басу керек. Ашылған парақшада Add route батырмасын басу қажет, жаңа жол қосылады. Мұнда Destination ретінде нөлдермен CIDR block көрсетеміз, бұл интернет CIDR block және Target ретінде жаңа NAT gateway таңдаймыз, содан кейін Save changes батырмасын басамыз. Осылайша біз жаңа NAT gateway құрдық, Private Subnet 2 ресурстары үшін осы NAT gateway арқылы трафик ағынын баптадық. Осылайша біз екінші тапсырманы аяқтап, келесіге өте аламыз. Біз үшінші тапсырманы бастаймыз, бұл жерде public subnet ішінде bastion host құру керек болады. Ол үшін EC2 сервисіне өтуіміз қажет, сервис іздеу жолағына EC2 деп терейік. Бірінші сілтеме – бізге қажет сілтеме, жақсы. EC2 сервисінің басты парақшасында Launch instance батырмасын басу керек, жаңа EC2 инстанс үшін қажетті мәліметтерді енгізу парақшасы ашылады. Name ретінде Bastion Host көрсетеміз, Application and OS бөлігінде Amazon Linux 2023 AMI таңдаймыз, Instance type ретінде t2.micro көрсетеміз, Key pair ретінде vockey таңдаймыз. Network settings бөлімінде өзгерістер енгізу үшін Edit батырмасын басу қажет болады. VPC ретінде Lab VPC таңдаймыз, ал Subnet ретінде Public Subnet 1 көрсетеміз. Auto-assign public IP үшін Enable таңдаймыз және жаңа security group жасаймыз. Бұл security group менің ағымдағы IP-мекенжайым үшін ssh трафикке рұқсат береді, содан кейін экранның оң жақ жоғарғы бұрышындағы Launch instance батырмасын баса аламыз. Инстанс сәтті құрылғаны туралы хабарлама көреміз. Ол толықтай қосылымға дайын болғанға дейін біраз уақыт қажет, бастапқыда Status check - Initializing болады, парақшаны мезгіл-мезгіл жаңартып тұру керек. Біраз уақыттан кейін 2/2 checks passed деген хабарлама көреміз, бұл bastion host толықтай іске қосылғанын және оған қосыла алатынымызды білдіреді. Жақсы, біз bastion host-ты дайындадық, осы арқылы үшінші тапсырманы аяқтаймыз және келесісіне өте аламыз. Біз төртінші тапсырмаға жеттік, мұнда launch template құрамыз. Оны жасау үшін сол жақтағы навигациялық мәзірден Launch templates бөлімін таңдаймыз. Бұл AWS аккаунтында бұрын launch templates жасалмағандықтан, тиісті парақша ашылады. Create launch template батырмасын басу қажет. Жақсы, біз жаңа launch template жасау парақшасына өттік, Launch template name ретінде webserver деп көрсетеміз. Auto Scaling guidance үшін белгіні қойып, төменге жылжимыз, мұнда бізге өзіміздің кастомды AMI таңдау қажет болады. Ол үшін келесі бөлімде My AMIs қойындысын, одан кейін фильтр ретінде Owned by me таңдаймыз және ашылған тізімнен Cafe WebServer Image таңдау қажет. Instance type бөлімінде t2.micro көрсетеміз, Key pair ретінде vockey таңдаймыз, ал Network settings бөлімінде атауында CafeSG бар security топ таңдау қажет. Төмен қарай жылжытайық, Resource tags бөлімінде Key ретінде Name, ал Value ретінде webserver көрсету қажет және Resource types бөлігінде міндетті түрде Instances таңдау керек. Бұл дегеніміз осы launch template арқылы жасалған барлық инстанстарға автоматты түрде осы тегтер байланысады. Төменірек Advanced details бөлімі болады, оны ашу қажет және IAM Instance Profile бөлімінде CafeRole рөлін таңдау керек. Содан кейін экранның оң жақ төменгі бұрышындағы Create launch template батырмасын баса аламыз. Бізді келесі парақшаға бағыттайды, launch template сәтті құрылғаны туралы хабарлама көреміз. Сонымен қатар View launch template батырмасын басып, ресурс парақшасын ашып, оның мәліметтерін көруімізге болады. Осылайша біз төртінші тапсырманы орындадық және келесіге өте аламыз. Біз бесінші тапсырмаға жеттік, бұл жерде Auto Scaling group құрамыз. Ол үшін сол жақтағы навигациялық мәзір арқылы Auto Scaling groups бөлімін таңдау қажет. Одан кейін Create Auto Scaling group батырмасын басу керек, бізді осы ресурсты жасау парақшасына жібереді. Name ретінде LabASG көрсетеміз, ASG – Auto Scaling group-тың қысқартылған түрі, Launch template ретінде webserver launch template таңдаймыз және парақтың төменгі жағындағы Next батырмасын басамыз. Келесі парақшада желі параметрлерін көрсету қажет болады. Мұнда VPC ретінде Lab VPC таңдаймыз, availability зоналар ретінде us-east-1a және us-east-1b көрсетеміз, олардың әрқайсысы үшін private subnet таңдаймыз — Private subnet 1 және Private subnet 2. Жақсы, енді төмен қарай жылжып, Next батырмасын басамыз. Келесі парақшада load balancer-мен байланыс орнатылады, бірақ ол әлі құрылмағандықтан, No load balancer таңдаймыз. Сондай-ақ, No VPC Lattice service таңдаймыз, парақшаның төменгі жағына дейін жылжып, Next батырмасын басамыз. Келесі парақшада Auto Scaling group көлемін таңдаймыз: Desired capacity және Minimum capacity ретінде 2, Maximum capacity ретінде 6 көрсетеміз. Сонымен қатар Scaling policy құрамыз, бұл Target tracking scaling policy болады. Атауы ретінде Target tracking policy, метрика ретінде Average CPU utilization, Target value ретінде 25, ал Instance warmup ретінде 60 секунд көрсетеміз. Одан кейін экранның оң жақ төменгі бұрышындағы Next батырмасын басу қажет. Келесі парақшада хабарламалар бапталады, бірақ бұл бізге қажет емес, сондықтан Next батырмасын басамыз. Тегтер де қажет емес, сондықтан Next батырмасын басамыз. Соңғы парақша – бұл Review, яғни енгізілген параметрлерді көруге болады. Егер бәрі дұрыс болса, Create Auto Scaling group батырмасын басамыз. Бұл батырманы басқан соң, біз Auto Scaling groups тізіміне өтеміз. Auto Scaling group пайда болады және оның статусында Updating capacity деп жазылады. Бұл дегеніміз, қазір 2 инстанс құрылып жатыр, себебі біз Desired capacity ретінде 2 көрсеткен едік. Қазір бұл инстанстар шынымен құрылып жатқанын тексерейік. Ол үшін EC2 сервисіне өту керек, іздеу жолағына EC2 деп тереміз. Инстанстар тізімін ашқанда, екі инстанс құрылып жатқанын көреміз және олардың атауы — webserver. Бұл launch template құру кезінде көрсетілген тег мәні. Жақсы, біз Auto Scaling group құрдық және бесінші тапсырманы аяқтадық. Біз алтыншы тапсырмаға жеттік, мұнда load balancer құрамыз. Ол үшін сол жақтағы навигациялық мәзір арқылы Load balancers бөлімін таңдаймыз. Бізді load balancers тізімі бар парақшаға бағыттайды, мұнда Create load balancer батырмасын басу қажет. Алдымен бізден load balancer түрін таңдау сұралады, бізге ALB, яғни Application Load Balancer қажет, сондықтан сәйкес Create батырмасын басамыз. Бізді Application Load Balancer құру парақшасына жібереді. Load balancer name ретінде webserver-alb, Scheme ретінде Internet-facing, ал IP address type ретінде IPv4 таңдаймыз. Сәл төмен қарай жылжимыз, желі параметрлері бөлімінде VPC ретінде Lab VPC көрсетеміз. Mappings бөлімінде екі availability зона таңдау қажет: us-east-1a және us-east-1b, олардың әрқайсысы үшін сәйкесінше Public Subnet 1 және Public Subnet 2 таңдаймыз. Сәл төмен жылжып, security тобы таңдалады, біз оны әлі құрған жоқпыз, сондықтан сәйкес сілтемені басып, жаңа security топ жасау парақшасына өтеміз. Бұл парақшада Security group name ретінде alb-sg енгіземіз, sg — security group дегенді білдіреді. VPC ретінде Lab VPC көрсетеміз, бір inbound rule қосу қажет, ол үшін Add rule батырмасын басамыз. Type ретінде HTTP таңдаймыз, қалған Protocol және Port range автоматты түрде TCP және 80 болып толтырылады. Source ретінде Anyway IPv4 көрсетеміз, келесі жолда интернет CIDR block, яғни нөлдермен CIDR block автоматты түрде орнатылады. Содан кейін парақшаның соңына дейін жылжып, Create security group батырмасын басамыз. Одан кейін бізді ресурс парақшасына қайта бағыттайды. Экранда security тобы сәтті құрылғаны туралы хабарлама көреміз. Енді бұл қойындыны жабуға болады және load balancer құру парақшасына қайта ораламыз. Бұл жерде Жаңарту батырмасын басып, жаңа security тобы — alb-sg таңдау қажет. Сәл төменірек Listeners and routing бөлімі бар, яғни трафик түріне сәйкес target топты көрсетуге болады, бізде бұл HTTP 80. Бұл трафик тиісті target топқа бағытталады. Себебі target топ әлі құрылмаған, сілтемені пайдаланып target топты құру парақшасына өтеміз. Бұл парақшада Target type ретінде Instances таңдаймыз, Target group name ретінде webserver-tg көрсетеміз, tg – target group дегенді білдіреді. Қалған параметрлерді әдепкі күйінде қалдырып, Next батырмасын басамыз. Келесі парақшада таргеттерді тіркеу ұсынылады, бірақ әзірге бұл қажет емес, сондықтан парақшаның соңына дейін жылжып, Create target group батырмасын басамыз. Жақсы. Target топ сәтті құрылды, парақша үстінде тиісті хабарлама көреміз. Енді бұл қойындыны жабамыз және load balancer құру парақшасына қайта ораламыз. Бұл жерде Target топтар тізімін жаңарту үшін Жаңарту батырмасын басу қажет. webserver-tg атты target топты таңдаймыз да, парақшаның соңына дейін жылжимыз. Экранның төменгі оң жағында Create load balancer батырмасын басу қажет. Біз келесі парақшаға өтеміз және load balancer сәтті құрылғаны туралы хабарлама көреміз. Енді View load balancer батырмасын басуға болады, load balancer тізімінде оны және Provisioning күйін көреміз. Сәл күтейік те, парақшаны жаңартайық. Жақсы, load balancer толық дайын, күйі — Active деп көрсетілген. Енді бұл load balancer-ді Auto Scaling group-пен байланыстыру қажет. Ол үшін сол жақтағы навигациялық мәзір арқылы Auto Scaling groups бөліміне өтеміз. Содан кейін LabASG ресурсының негізгі парақшасын ашып, Details қойындысын таңдаймыз. Төмен қарай жылжып, Load balancing бөліміне жетіп, Edit батырмасын басамыз. Сол жерде байланыстыратын load balancer-ді таңдауға болады. Бізді Application Load Balancer қызықтырады, тиісті ұяшыққа белгі қоямыз және ашылмалы тізімнен webserver-tg таңдаймыз. Яғни біз тікелей load balancer-ге емес, target топ арқылы байланыстырамыз. Жақсы. Енді экранның төменгі оң жағында Update батырмасын баса аламыз. Осылайша load balancer құрылды, ол Auto Scaling group-пен target топ арқылы байланыстырылды. Жақсы. Біз бұл тапсырманы аяқтадық және келесіге өте аламыз. Біз жетінші тапсырмаға келдік, мұнда веб-қосымшаның жұмысын тексереміз. Ол үшін сол жақтағы навигациялық мәзір арқылы Load balancers бөліміне өтіп, өзіміздің load balancer-ді таңдаймыз. Содан кейін Details қойындысынан DNS name табамыз — бұл біздің load balancer сілтемесі. Оны ашайық, бірақ ашпас бұрын соңына /cafe қосу керек, сонда веб-қосымша ашылады. Егер сіз осындай парақшаны көрсеңіз, бұл осы уақытқа дейінгі әрекеттердің дұрыс орындалғанын және қосымшаның жұмыс істеп тұрғанын білдіреді. Енді келесі тапсырмаға өтуге дайынбыз. Біз сегізінші тапсырмаға келдік және мұнда жүктеме жағдайында автомасштабтауды тексереміз. Ол үшін VPC сервисіне өту қажет, іздеу жолағына жазып, бірінші сілтемені басамыз. Мұнда сол жақтағы навигациялық мәзір арқылы security group тізіміне өтеміз. Бізді application серверлеріне байланған security тобы қызықтырады — бұл CafeSG. Оны таңдайық, төменгі қойындыларда Inbound rules бөліміне өтіп, Edit inbound rules батырмасын басамыз. Не істеуіміз керек: bastion host-тан application серверлерге ssh арқылы қосылу үшін оған рұқсат беруіміз қажет. Ол үшін ашылмалы тізімнен тиісті security тобы таңдалады. Қай security топ екенін bastion host баптауларынан анықтай аламыз, сондықтан сол жақтағы навигацияны пайдаланамыз. Инстанстар тізімін ашамыз, bastion host таңдаймыз және Security қойындысында оған қандай security топ байланғанын көреміз. Жақсы, енді жаңа rule қосуға болады, Type ретінде SSH көрсетеміз, ал Source бөлімінде Custom таңдаймыз. Бұл кезде sg деп тере бастаймыз және bastion host-қа байланған security топты таңдаймыз. Жақсы. Енді Save rules батырмасын басу қажет. Біз ресурс парақшасына өтеміз және экранның жоғарғы жағында inbound rules пен security топ сәтті жаңартылғаны туралы хабарламаны көреміз. Енді application серверлердің кез келгеніне қосылу қажет. Қосылу bastion host арқылы жүзеге асады, сондықтан PuTTY бағдарламасында кейбір баптауларды жасау қажет. PuTTY-де ресми сайттан жүктелетін бөлек модуль бар — Pageant деп аталатын шағын бағдарлама, оны жүктеп, іске қосу қажет. Бағдарлама іске қосылғаннан кейін Add key батырмасын басып, application серверлер үшін жасаған жеке кілтті жүктейміз және Close батырмасын басамыз. Енді PuTTY бағдарламасын іске қосу қажет, сол жақтағы навигация мәзірінен Auth бөлімін таңдап, Allow agent forwarding деген жолға белгі қою қажет. Содан кейін, PuTTY басты парақшасына оралып, bastion host-қа арналған vockey жеке кілтін және оның public IP-адресін енгізіп, Open батырмасын басамыз. Егер бәрін дұрыс істесек, bastion host-қа қосыла аламыз. Енді application серверлердің кез келгенінің жеке IP-адресін тауып, келесі команданы жазу қажет. Pageant бағдарламасында веб-серверлердің жеке кілттері көрсетілгендіктен, осы команданы енгізу жеткілікті және біз веб-серверге қосыла аламыз. Жақсы, бұл өте ыңғайлы емес пе? Енді жасанды жүктеме жасау бағдарламасын жүктеу қажет, бұл команда арқылы оны жүктейміз. Кейін оны орнату керек және келесі команда арқылы бағдарламаны іске қосамыз. Ол біздің процессорларға 10 минут бойы 100% жүктеме береді. Енді Auto Scaling group-қа өту қажет. Сол жақтағы навигациялық мәзірді пайдаланып, Auto Scaling groups бөліміне өтеміз. LabASG атты Auto Scaling group таңдаймыз және Instance management қойындысына өтеміз. Басында 2 инстанс болады, егер парақшаны жаңартып отырсақ, олардың саны 6-ға дейін артады. Яғни Auto Scaling group пен load balancer қосымша жүктемені байқады және оны өңдеу үшін жаңа инстанстар қосты. Осылайша біз AWS бұлтында IT-инфрақұрылымымыздың жоғары қолжетімділігі мен автомасштабталуын баптадық және зертханалық жұмысымызды аяқтадық. Енді соңғы кезең қалды — жұмысымыздың автобағалауын іске қосып, барлық жүйелерден сәтті шығу қажет. Алдымен зертхана парақшасына қайта оралып, Submit батырмасын басып, бұл әрекетті растау қажет. Біраз уақыт өткен соң нәтижелерді көреміз, менің жағдайымда біз 36-дан 36 балл алдық. Егер сіз қажетті балл ала алмасаңыз немесе нәтижеңізді жақсартқыңыз келсе, тиісті тапсырмаға қайта оралып, түзетулер жасап, автобағалауды қайта іске қоса аласыз. Осылайша зертханалық жұмысты аяқтаймыз. Ол үшін End lab батырмасын басу керек, әрекетті растаймыз және бұл қойындыны жабуға болатыны туралы хабарламаны көреміз. Енді AWS Management Console-де бір ғана қойындыны қалдырып, жоғарғы оң жақ бұрыштан пайдаланушы атын басып, ашылған тізімнен Sign out батырмасын басу қажет. Жақсы, сіздерді құттықтаймын!
