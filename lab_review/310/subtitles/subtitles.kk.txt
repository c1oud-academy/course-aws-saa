Қайырлы күн, құрметті студенттер. Зертханалық жұмысты талқылау сессиясында сіздерді көргеніме қуаныштымын. Бүгінгі зертханалық жұмыста біз монолитті Node.js қосымшасын микросервистерге бөлетін боламыз. Ал, бастайық. Бірінші тапсырманы бастаймыз. Бірінші тапсырма аясында қосымшамыздың кодын жергілікті ортаға көшіреміз. Біз Cloud9 IDE-де жұмыс істейміз, сондықтан осы сервиске өтуіміз керек. Бір ғана environment болады. Оны ашайық. Оны жасаған соң қосымшамыздың барлық қажетті файлдарын көшіретін команданы орындауымыз керек. Экранның сол жағында файлдар мен папкалар құрылымын көреміз. Онда бірдей қосымшаның әр түрі үшін үш папка пайда болды. Егер бәрі дұрыс көшірілсе, бірінші тапсырманы аяқтап, келесіге көшеміз. Екінші тапсырманы бастаймыз. Бұл тапсырмада монолитті қосымшамызды іске қосып, жұмысын тексереміз. Алдымен қосымшамызды дайындауымыз керек. Бірінші папкаға өтіп, екі команданы орындаймыз. Бұл командалар koa және koa-router Node модульдерін орнатады. Олар қосымшаның дұрыс жұмыс істеуі үшін қажет. Содан кейін осы папканың мазмұнымен танысамыз. Егер package.json файлын ашсақ, қосымшада қолданылатын Node модульдерінің тізімін көреміз. Сондай-ақ монолитті қосымшаны іске қосу командасын да көресіз. Келесі db.json файлы — дерекқорды эмуляциялайтын статикалық JSON файл. Онда пайдаланушылар, тақырыптар және олардың пікірлері туралы ақпарат бар. Келесі index.js файлы — қосымшаның кіріс нүктесі, ал server.js — қосымшаның өзегі, ол сұрауларды бағыттап, тиісті жауап береді. Енді қосымшаны іске қосып көрейік. Терминалдың төменгі бөлігінде npm start командасын енгіземіз. Қосымша іске қосылып, сұрауларды өңдеуге дайын болады. Сұрауларды орындау үшін жаңа терминал терезесін ашуымыз керек. Ол үшін терминалдың жоғарғы жағындағы жасыл шеңберді басып, New terminal опциясын таңдаймыз. Мұнда келесі команданы енгіземіз. Нәтижесінде барлық пайдаланушылардың тізімін JSON құжаты түрінде аламыз. Бірінші терминал терезесіне оралсақ, веб-сервердің /api/users жолы бойынша GET сұрауды орындағанын көреміз. Енді, тағы бірнеше API шақыруын жасайық. Төртінші пайдаланушының мәліметтерін алайық. Содан кейін барлық тақырыптардың тізімін алып, бірінші тақырып бойынша барлық пікірлерді алайық. Жақсы, қосымшаның жұмысын тексердік. Сондай-ақ веб-серверге жасалған барлық GET сұрауларын көріп тұрмыз. Енді веб-серверді тоқтата аламыз. Ол үшін CTRL+C пернелер тіркесімін басу керек, осылайша екінші тапсырма аяқталады. Үшінші тапсырманы бастаймыз. Бұл тапсырмада монолитті қосымшамызды контейнерде орнатамыз, ол үшін Amazon ECS сервисін қолданамыз. Бастамас бұрын қосымшамыздың файлдарында қандай өзгерістер болғанын қарайық. package.json файлын ашсақ, сәл өзгергенін көреміз. Содан кейін server.js файлын ашсақ, контейнерде қосымша дұрыс жұмыс істеуі үшін бір жол қосылғанын көреміз. Сондай-ақ жаңа файл пайда болды, ол — Docker файлы. Бұл болашақ Docker-кескінін сипаттайтын файл. Енді AWS Management Console-ге өтіп, ECR сервисін ашу керек. Бұл біздің Docker-кескіндеріміз сақталатын сервис. Get Started батырмасын басайық, жаңа репозиторий құру парақшасы ашылады. Репозиторийді mb-repo деп атап, экранның төменгі оң жағындағы Create Repository батырмасын басамыз. Жақсы, репозиторий құрдық, енді осы репозиторийде кескін жасауымыз керек. Ол үшін AWS CLI-ді жаңартып, келесі команданы орындаймыз. Барлығы дайын болған соң, орта айнымалыларын жаңарту үшін тағы бір команданы іске қосуымыз керек. Енді репозиториімізге қайта оралып, View Push Comments батырмасын басуымыз керек. Егер экранның жоғарғы оң жағындағы хабарлама жабылған болса, репозиторийді белгілеп, жоғарғы оң жақтағы батырмалар тізімінен View Push Comments пәрменін көресіз. Оны басайық, сонда төрт командасы бар қалқымалы терезені көресіз. Бұл — біздің Docker-кескінімізді ECR сервисіне жариялау үшін дәл осы ретпен орындау керек командалар. Қалқымалы терезенің жоғарғы бөлігінде екі қойынды бар екеніне назар аударыңыз. Бірінші қойынды macOS және Linux үшін, екіншісі Windows үшін. Біз Cloud9 IDE-де жұмыс істегендіктен, бізді бірінші қойынды қызықтырады. Бірінші команданы көшіріп, IDE-ге енгізейік. Содан кейін екінші папка түбіріне өтуіміз керек. Енді екінші команданы көшіріп, IDE-де іске қосамыз. Бұл команданың сәтті орындалғанын соңғы екі жолдан көреміз. Қалған хабарламаларды елемеуге болады. Енді үшінші және төртінші командаларды іске қосамыз. Үшінші команда сәтті орындалса, ештеңе шығармайды — бұл қалыпты жағдай. Төртінші команданы іске қосқан соң, біздің кескініміздің ECR сервисіне жүктелу процесін көрсететін толық ақпаратты көресіз. Енді кескініміздің сервиске түскенін тексерейік. Ол үшін репозиториіміздің басты парақшасын ашып, кескіндер тізімінен жалғыз кескінді көреміз. Осы жерде кескіннің URI-ын көшіруіміз керек. Оны келесі тапсырмада қолданамыз. Осылайша үшінші тапсырманы аяқтап, келесіге өте аламыз. Төртінші тапсырманы бастаймыз. Бұл тапсырмада монолитті қосымшамызды Amazon ECS сервисін қолданып орнатамыз. Ол үшін сервис іздеу жолын қолданып ECS деп тереміз, нәтиженің бірінші сілтемесі — бізге керек сілтеме. Сервис басты парақшасына кірген соң, ескі интерфейске ауысамыз және кластерлер тізімі парақшасында Create Cluster батырмасын басамыз. Мұнда EC2 Linux + Networking опциясын таңдап, кластер құрудың екінші парақшасына өтеміз. Бұл парақшада жаңа кластердің атауын енгіземіз, EC2 инстанс түрін және санын көрсетеміз. Содан кейін желі туралы ақпарат енгіземіз: жаңа VPC құрамыз, CIDR блокты және сабнеттердің CIDR блоктарын көрсетеміз. Төменірек жаңа Security топ құрамыз және әдепкі Inbound rule қалдырамыз, ол интернеттен 80-портқа рұқсат береді. Одан төмен контейнеріміз үшін IAM рөлін құру опциясы бар, мәнін әдепкіде қалдырамыз — Create New Role, кейін экранның төменгі оң жағындағы Create батырмасын басамыз. Бізді кластер құру парақшасына бағыттайды, ол үш бөліктен тұрады, үшеуі сәтті орындалса, экранның жоғарғы жағындағы View Cluster батырмасын басамыз. Кластердің басты парақшасына өтеміз, мұнда ECS Instances қойындысын басу керек. ECS Instances бірден шықпайды, сондықтан екі минуттан кейін тізімді жаңартып, Active күйінде тұрған екі ECS инстансын көресіз. Келесі қадам — Task Definition жасау, ол үшін сол жақтағы навигация мәзірінен тиісті бөлімді таңдаймыз. Ашылған парақшада Create New Task Definition батырмасын басамыз. Содан кейін EC2 опциясын таңдап, Next Step батырмасын басамыз. Ресурс жасаудың екінші қадамында Task Definition атауын енгізіп, төмен қарай жылжып, Add Container батырмасын басамыз. Мұнда контейнеріміз туралы ақпарат енгіземіз, яғни Container Name. Image өрісіне контейнеріміздің URL-ын қоямыз, оны біз бұрын көшірдік, Memory Limit үшін 256 мәнін көрсетеміз және Container Port ретінде 3000 енгіземіз. Содан кейін экранның төменгі оң жағындағы Add батырмасын басамыз. Қалған баптауларды әдепкідей қалдырып, парақшаның соңына жылжып, Create батырмасын басамыз. Біз Task Definition басты парақшасына өтеміз, ол сәтті жасалғанын көреміз және бұл Task Definition-ның бірінші нұсқасы екенін байқаймыз. Енді келесі қадам — Application Load Balancer-ді баптау. Ол үшін сервис іздеу жолына balancer деп жаза бастаймыз, нәтижеден Load Balancers тізіміне тікелей сілтемені көреміз, соны басайық. Ашылған парақшада Create Load Balancer батырмасының қасындағы үшбұрышты басып, Load Balancer түрін таңдау керек, бізді Application Load Balancer қызықтырады. Осыны жасаған соң, бізді жаңа ресурс құру парақшасына жібереді, мұнда Load Balancer атауын енгіземіз. Одан кейін төменгі жағындағы желі баптауларында өзіміздің VPC-ні таңдап, Mappings бөлімінде екі Availability Zone-ға да белгі қойып, сәйкес сабнеттерді таңдаймыз. Төменірек бар Security тобын таңдап, Listeners and Routing бөлімінде жаңа Target топ құру керек болады. Ол үшін тиісті сілтемені басамыз, бізді браузердің жаңа қойындысында жаңа ресурс құру парақшасына жібереді, бұл қойындыны жаппаймыз. Жаңа Target топ құру парақшасында Instances түрін таңдау керек. Одан кейін жаңа Target топ атауын енгізіп, Protocol ретінде HTTP және 80-портты көрсетеміз. VPC өрісінде өзіміздің VPC-ні таңдау керек. Advanced Health Check Settings бөлімінде Healthy Threshold мәнін 2 деп, Timeout — 5, Interval — 6 секунд етіп көрсетіп, төменгі оң жақтағы Next батырмасын басамыз. Бізді таргеттерді тіркеу парақшасына жібереді, екі EC2 инстансымызды таңдап, төменгі оң жақтағы Create Target Group батырмасын басамыз. Енді жаңа Application Load Balancer құруды аяқтай аламыз, ол үшін осы ресурс құру қойындысына қайта оралып, Target Group тізімін жаңарту керек. Target тобымызды көрген соң, оны таңдап, парақшаның соңына жылжып, Create Load Balancer батырмасын басамыз. Осыны жасаған соң, бізді Load Balancers тізімі парақшасына жібереді. Load Balancer-іміз Provisioning күйінде тұрғанын көреміз. Ол Active күйіне өткенше, Security топта кейбір өзгерістер жасайық. Ол үшін Load Balancer-імізді таңдап, Security қойындысын ашамыз, мұнда өзіміздің Security топты көреміз. Оның ID-н есте сақтап немесе көшіріп алып, Security топ атауын басамыз, бізді Security топ басты парақшасына жібереді. Мұнда бізді Inbound Rules қойындысы қызықтырады, соны таңдап, Edit Inbound Rules батырмасын басамыз. Inbound Rules өңдеу парақшасы ашылған соң, Add Rule батырмасын басу керек. Custom TCP таңдап, Port Range өрісіне тиісті мәнді енгізіп, Source ретінде өзіміздің Security топты көрсетеміз. Содан кейін Save Rules батырмасын басамыз, жақсы. Бұл баптауларды жасап болғанша, Load Balancer-іміз Active күйіне өтіп үлгереді, осыдан кейін келесі тапсырмаға өте аламыз. Енді Task Definition парақшасына қайта оралып, ол үшін жаңа сервис құру керек. Ол үшін Actions батырмасын басып, Create Service опциясын таңдаймыз, бізді жаңа сервис құру парақшасына жібереді. Type ретінде EC2 таңдап, жаңа сервис атауын енгіземіз, Type — REPLICA, ал тапсырмалар саны — 1. Содан кейін төменгі оң жақтағы Next Step батырмасын басамыз. Келесі қадамда Load Balancer түрін таңдаймыз, бұл Application Load Balancer. Төменірек Add to Load Balancer батырмасын басайық. Жаңа өрістер шығады, Production Listener Port ретінде 80:HTTP, ал Target Group Name ретінде біз бұрын құрған Target топты таңдап, Next Step батырмасын басамыз. Үшінші қадамда Auto Scaling баптау ұсынылады, бірақ біз оны зертханада баптамаймыз, сондықтан Next Step басамыз. Соңғы парақша — Review парақшасы, егер бәрі дұрыс енгізілсе, төменгі жағындағы Create Service батырмасын басамыз. Бізді жаңа ресурстарды құру статусы парақшасына жібереді, үш қадам да сәтті орындалса, төменгі оң жақтағы View Service батырмасын баса аламыз. Осыны басқан соң, біз кластер ішіндегі сервистің басты парақшасына өтеміз. Төменгі бөлігінде бірнеше қойынды бар, бізді Tasks қойындысы қызықтырады, біраз күтіп, тапсырмалар тізімін жаңартамыз. Бір ғана тапсырмамыз көрсетіліп, күйі Running болса, келесі тапсырмаға көше аламыз. Жақсы, енді қосымшамыздың жұмысын тексеруге болады. Load Balancer-імізге өтіп, оның DNS Name көшірейік. Осы URL-ды браузердің жаңа қойындысында ашқанда, Ready to receive requests деген жауап көреміз. Егер осы URL-ға /api қоссақ, API Ready to receive requests деген басқа жауап аламыз. Пайдаланушылар тізімін, тақырыптарды және т.б. алу үшін API командаларын өзіңіз орындап көріңіз. Жалпы қосымша мен API дұрыс жұмыс істеп тұрғанын көріп тұрмыз, енді келесі тапсырмаға өте аламыз. Алдыңғы тапсырмада біз монолитті қосымшаны ECS сервисінде контейнерде орнаттық. Енді микросервис қосымшамен жұмыс істейміз, бесінші тапсырмада оны дайындаймыз, барлық қажетті кескіндерді құрамыз, IT-инфрақұрылымға өзгерістер енгіземіз және алтыншы тапсырмада оны орнатып көреміз. Ендеше бастайық. Алдымен IDE-ге өтуіміз керек. Барлық қажетті файлдарды біз бұған дейін жүктеп алғанбыз, сондықтан қазір бәрі дайын болуы керек, бізді үшінші папка қызықтырады. Үшінші папкада барлық файлдар үш ішкі папкаға бөлінген: Users, Threads және Posts. Әр папкада өзінің деректер базасы, Docker файлы, package.json және server.js бар. Ең көп server.js файлы ерекшеленеді, өйткені онда трафикті қайта бағыттау логикасы жазылған: API Users шақырулары бірінші микросервиске, ал қалғандары тиісті микросервистерге бағытталады. Енді әр микросервис үшін Docker-кескін жасауымыз керек, ол үшін ECR сервисіне өтіп, жаңа репозиторий құрамыз. Репозиторий атауы — mb-users-repo, бұл Users микросервисіне арналған. Ресурс құру парақшасында соңына дейін жылжып, Create Repository батырмасын басамыз. Біз бірінші микросервис үшін репозиторий құрдық, дәл осылай қалған екі микросервис үшін де mb-threads-repo және mb-posts-repo репозиторийлерін құрамыз. Енді төрт команданы орындау керек, нәтижесінде Docker-кескін жасалып, ECR репозиторийіне жүктеледі. Бұл қалай жасалатынын біз білеміз: репозиторийді таңдап, оң жақ жоғарғы бұрыштағы View Push Commands батырмасын басу керек. Лаборатория тапсырмасы бойынша бірінші команда өткізіліп кеткен, бірақ біз оны өткізбеуіміз керек, алдымен міндетті түрде сол команданы орындаймыз. Содан кейін қалған үш команданы орындаймыз. Егер бірінші команданы орындамасақ, ECR сервисінде авторизация болмайды да, кескінді жүктей алмаймыз. Осыны орындап болған соң, кескіннің шынымен пайда болғанын тексере аламыз. mb-users-repo репозиторийінің басты парақшасына өтіп, бір ғана image — жаңа жасағанымызды көреміз. Дәл осылай mb-threads-repo және mb-posts-repo репозиторийлері үшін де кескіндер жасау керек. Енді соңғы, алтыншы тапсырманы бастаймыз, мұнда микросервис қосымшаны орнатамыз. Алдымен ECS сервисіне өтіп, әр микросервис үшін Task definition құрамыз. Task definition жасау кезінде Type — EC2 деп көрсетеміз, содан кейін task definition атауын енгізу керек. Төменірек Add container батырмасын басып, Container name және Image URI енгіземіз, оны тиісті image репозиторийінен көшіреміз. Memory limit — 256, Container port — 3000 деп көрсетіп, төменгі оң жақтағы Add батырмасын басамыз. Басты парақшада да барлық қажетті деректерді енгізіп болған соң, төменгі оң жақтағы Create батырмасын басамыз. Біз task definition-ді 1-нұсқада жасаймыз. Бұл тапсырма тізімде шығады, дәл осылай posts және threads микросервистері үшін де task definition жасау керек. Application load balancer бізде бұрыннан бар, оны қайта пайдаланамыз, бірақ әр микросервис үшін жеке target топтар жасау керек. Сервис іздеу жолына target groups деп жаза бастаймыз. Бірінші шыққан сілтеме — бізге керек сілтеме. Соны ашып, парақшаның ішінде Create target group батырмасын басамыз. Type ретінде Instances таңдап, users микросервисіне арналған target топ атауын mb-lb-users-target-group деп енгіземіз. Содан кейін қосымшамыздың VPC-ін таңдап, Advanced settings бөлімінде алдыңғы target топ үшін енгізген мәндерді көрсетеміз. Одан кейін төменгі оң жақтағы Next батырмасын басамыз. Келесі парақшада таргеттерді тіркеу ұсынылады, бірақ бізге бұл қажет емес, сондықтан төменгі жағындағы Create target group батырмасын басамыз. Бізді target group тізімі парақшасына жібереді, мұнда топтың сәтті құрылғаны туралы хабарламаны көреміз. Дәл осылай қалған екі микросервис үшін де target топ жасау керек. Нәтижесінде тағы екі қосымша target топ пайда болады. Енді load balancer парақшасына өтіп, қажетті өзгерістер енгіземіз. Load balancer жағында Listeners and rules қойындысын ашып, бір ғана ережені таңдап, Manage rules батырмасын басамыз. Ашылған тізімнен Add rule батырмасын басамыз. Әр микросервис үшін жаңа ереже құрамыз. Қазір оны users микросервисінің мысалында қарастырамыз. Бірінші парақшада ештеңе енгізбей, Next батырмасын басамыз. Екінші парақшада шарттар қосу керек. Add conditions батырмасын басып, Rule condition types ішінен Path таңдаймыз. Жол ретінде /api/users* деп жазамыз және соңында жұлдызша қойылады, осылайша /api/users бастапқысы бар барлық URL осы ережеге түседі. Confirm батырмасын басып, келесі парақшаға өтеміз. Келесі парақшада Action таңдау керек, Forward to target groups таңдаймыз да, target group тізімінен users микросервисіне арналған target топты таңдап, төменгі оң жақтағы Next батырмасын басамыз. Содан кейін осы ереженің Priority мәнін көрсету керек, ол бірінші болсын, сосын Next батырмасын басамыз. Соңғы парақша — Review парақшасы, бәрі дұрыс толтырылған болса, Create батырмасын басамыз. Содан кейін rules тізімінде жаңа ереже пайда болады, дәл осылай қалған екі микросервис — threads және posts үшін де жасаймыз, олардың приоритеттері сәйкесінше 2 және 3 болады. Енді тағы бір-екі өзгеріс енгіземіз: Add rule батырмасын басып, екінші парақшаға өтеміз де, келесі шартты қосамыз. Шарт түрі ретінде Path таңдаймыз да, путь ретінде / немесе /api деп көрсетеміз, бұл қосымшаның басты парақшасы немесе API басты парақшасы ашылған жағдай. Осы шартты жасайтынымызды растаймыз да, Next батырмасын басамыз. Action ретінде Forward to target groups таңдап, users микросервисінің target тобын көрсетеміз. Өйткені users микросервисінде server.js ішінде басты парақша мен API басты парақшасын өңдеу логикасы жазылған, сондықтан трафикті дәл осы микросервиске бағыттаймыз. Содан кейін Next батырмасын басып, Priority мәнін 4 деп көрсетеміз, төмендегі Next батырмасын басып, жаңа ережені құруды растаймыз. Енді әдепкі rule-ге өзгеріс енгізу керек. Оны белгілеп, оң жақ жоғарғы бұрыштағы Actions батырмасын басып, ашылған тізімнен Edit rule таңдаймыз. Action ретінде Return fixed response таңдау керек. Response code — 200 деп көрсетеміз (сәтті шақыру), ал Response body-ге кез келген мәтін жаза аламыз. Біздің жағдайда — Invalid request, содан кейін өзгертулерді сақтаймыз. Бұл ережені не үшін жасаймыз? Егер API-ге сұрау жіберілсе, бірақ жоғарыда жасалған ешбір ереже шарттарына сай келмесе, соңғы кезекте сіз енгізген мазмұны бар статикалық парақшаны қайтарамыз. Бұл кезде қосымшаның есептеу ресурстарын жұмсамаймыз, себебі URL бастапқыдан қате екенін білеміз. Бұл парақшада барлық rules тізімі көрсетілген, бұл — соңғы күйі. Алғашқы үш ереже — әр микросервиске арналған, төртіншісі — басты парақшаға немесе API басты парақшасына сұрау түскенде, бесінші — әдепкі ереже, ол жоғарыдағы ешбір ереже URL-ді өңдей алмаса, статикалық парақшаны қайтарады. Енді ECS кластеріндегі task definition үшін сервистер жасау керек. Бұл сервиске өтіп, сол жақтағы навигация мәзірінен Clusters таңдаймыз. Кластерімізді ашып, Services қойындысында Create батырмасын басамыз, мысал ретінде users микросервисінің сервисін құрамыз. Мұнда өзгерту керек барлық өрістер белгіленген, парақшаның төменгі жағында Next step батырмасын басамыз. Load balancer type ретінде ALB көрсетеміз, Role ретінде ecsServiceRole таңдаймыз, оны кластер құрған кезде жасағанбыз. Содан кейін load balancer-ді таңдап, Production listener port үшін 80:HTTP көрсетеміз. Ал Target group name ретінде users микросервисінің target тобын көрсетеміз. Осыдан кейін төменгі Next step батырмасын басамыз. Auto Scaling баптамаймыз, Next step батырмасын басамыз. Келесі Review парақшасында Create service батырмасын басамыз. Барлық ресурстар құрылғанша күтеміз, бәрі дайын болғанда және тиісті хабарлама шыққанда, төменгі оң жақтағы View service батырмасын басуға болады. Бізді кластердің басты парақшасына қайтарады, мұнда Tasks қойындысын таңдаймыз. Running статусымен сәтті іске қосылған task-ті көреміз, егер ол шықпаса, бірнеше минут күтіп, парақшаны жаңартыңыз. Жақсы, егер енді кластердің басты парақшасына оралып, Services қойындысын таңдасақ, users микросервисінің сервисін жасағанымызды көреміз. Дәл осылай қалған екі микросервис — threads және posts үшін де әрекет жасаймыз. Енді микросервис қосымшаның дұрыс жұмыс істеуі үшін, біз монолиттік қосымшаға арнап жасаған ең алғашқы сервиске өзгеріс енгізуіміз керек. mb-ecs-service сервисін таңдап, Update батырмасын басамыз. Содан кейін осы ресурсты өңдеу парақшасы ашылады. Өзгерту керек жалғыз өріс — тапсырма саны, оны 0 деп көрсетеміз, сонда бұл сервис қолданылмайды. Төменгі оң жақтағы Skip to review батырмасын басып, соңғы парақшада Update service батырмасын басамыз. Сервис сәтті жаңартылған соң, View service батырмасын басып, сервис парақшасына өтеміз. Мұнда Deployments қойындысы қызықтырады, Running count бағанында 0 болса, бәрін дұрыс жасадық. Енді қосымшамызды тестілеуге көше аламыз. Ол үшін біздің load balancer-ге өтіп, оның DNS name-ін көшіру керек, осы URL-ді ашайық. Монолитті қосымшаны орнатқан кездегідей дәл сол хабарламаны көреміз — Ready to receive requests. Егер URL-ге /api деп қосатын болсақ, дәл сондай хабарлама көреміз — API ready to receive requests. Енді API-імізді қолданып көрейік және қажетті жауап қайтып жатқанын тексерейік. /users деп қосамыз, бізге пайдаланушылар тізімі бар JSON қайтады. Содан кейін соңғы URL-ге /1 деп қосатын болсақ, бірінші пайдаланушы туралы ақпаратты көреміз. Енді жоқ URL енгізейік, мысалы /api/xyz, нәтижесінде біз көрсеткен мазмұны бар статикалық парақша қайтады, менің жағдайда — Invalid request. Егер бәрі дәл осылай болып, сіз де осындай жауап алсаңыз, құттықтаймын — біз ECS сервисін қолданып микросервис қосымшасын сәтті орнаттық. Жақсы, біз зертханалық жұмыстың ең соңғы бөлігіне келдік, мұнда автобағалау скриптін іске қосып, жұмысты аяқтаймыз. Алдымен зертханалық жұмыстың басты парақшасына оралып, Submit батырмасын басу керек. Содан кейін бұл әрекетті растау керек және біраз күтеміз, оң жақта бағаларымыз көрсетілген қойынды пайда болады. Егер ол шықпаса, экранның оң жақ жоғарғы бөлігіндегі Grades батырмасын басу керек. Менің жағдайымда мен 80 баллдың 80-ін алдым, бұл мені қанағаттандырады, енді зертханалық жұмысты аяқтауға болады. Егер сіз қажетті балл ала алмасаңыз және жақсартқыңыз келсе, қай тапсырмада балл жетпегенін қарап, сол тапсырмаға оралып, қажетті өзгерістер енгізіп, автобағалау скриптін қайта іске қосуға болады. Автобағалау скриптін іске қосу үшін ешқандай айыппұл жоқ, сондықтан оны қалағаныңызша іске қосуға болады. Енді зертханалық жұмысты аяқтау үшін AWS Management Console-да тек бір қойындыны қалдырып, экранның оң жақ жоғарғы бөлігінде пайдаланушы атыңызды басып, ашылған тізімнен Sign out батырмасын таңдаймыз. Содан кейін зертханалық жұмыстың басты парақшасына қайта оралып, End lab батырмасын басып, бұл әрекетті растау керек. Бізге AWS уақытша аккаунтын жою процесі сәтті басталғанын көрсететін хабарлама шығады және осы қойындыны жабуға болатыны айтылады. Осылайша біз зертханалық жұмыстың талдауын аяқтадық. Назарларыңызға рахмет, келесі белсенділіктерде кездескенше.
