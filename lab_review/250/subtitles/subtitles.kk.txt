Қайырлы күн, құрметті студенттер. Зертханалық жұмысты талқылаудың кезекті сессиясында сіздерді көргеніме қуаныштымын. Бүгінгі зертханалық жұмыстың тақырыбы — AWS бұлтында жоғары қолжетімді IT-инфрақұрылым құру. Ендеше, бастайық. Бірінші тапсырма. Бұл тапсырма аясында осы зертханалық жұмыс үшін AWS аккаунтында алдын ала дайындалған ресурстармен танысамыз. AWS Management Console басты парақшасынан бастаймыз. Мұнда сервис іздеу жолағын қолданып, VPC сервисін табу қажет. VPC сервисінің басты парақшасына кірген соң, ыңғайлы функция бар. Сол жақтағы навигациялық мәзірде, жоғарғы бөлігінде, VPC бойынша фильтрлеу мүмкіндігі бар, әрі қарай ашатын барлық парақшалар тек осы VPC-ге қатысты ресурстарды көрсетеді. Осыны істейік. Select a VPC ашылмалы тізімін басып, осы зертханалық жұмыс аясында жұмыс істейтін Lab VPC таңдау қажет. AWS аккаунтымыздағы ресурстарды шолуды бастаймыз, бізде қандай ресурстар бар екенін қараймыз. VPC-ден бастаймыз, сол себепті навигациялық мәзірден Your VPCs бөлімін таңдаймыз. Бізде бір ғана ресурс бар екенін көреміз — бұл күтілген нәтиже. Біз Lab VPC бойынша фильтр жасап тұрмыз, сондықтан тек сол көрініп тұр. Lab VPC-ні таңдайық, экранның төменгі бөлігінде осы ресурс жайлы ақпарат беретін бірнеше қойынды ашылады. Ең бірінші қойындыда VPC-нің CIDR блогын көруге болады — бұл 10.0.0.0/16, яғни осы VPC шамамен 65 мың IP-мекенжайын қамти алады. Енді subnets бөліміне өтейік, сол жақтағы навигациялық мәзірде Subnets пунктін таңдау қажет. Subnets тізімі бар парақша ашылады, VPC бағанына назар аударыңыз — барлық subnet-тер Lab VPC-ге байланған. Мысал ретінде бір subnet-ті қарастырайық, мысалы Public Subnet 1. CIDR блогына назар аударыңыз — 10.0.0.0/24, бұл 256 IP-мекенжайлық CIDR блогы және Lab VPC CIDR блогына кіреді. Осы subnet-ті таңдайық және төменгі жағындағы қойындылар тізімінен Route Table таңдаңыз. Екі route бар: біріншісі — бұл әдепкі route, ол VPC ішіндегі ресурстардың бір-бірімен байланысуына мүмкіндік береді. Екіншісінде Destination ретінде нөлдік CIDR блок көрсетілген — бұл интернет, ал Target ретінде Internet Gateway берілген, оны IGW префиксінен тануға болады. Бұл Public Subnet атауы ғана емес, шынымен де public subnet екенін көрсетеді, себебі ол интернетке шыға алады және интернеттен де қолжетімді. Енді Network ACL-ды қарастырайық, ол үшін сол жақтағы навигациялық мәзірде Network ACLs бөлімін таңдаймыз. Бұл парақшада бір ғана Network ACL көрсетілген, ол барлық төрт subnet-пен байланысты, әдепкі ACL болып табылады және Lab VPC-мен байланысқанын көреміз. Оны таңдап, Inbound Rules қойындысын ашайық. Екі rule бар, бұл әдепкі ережелер — кіріс және шығыс трафикке рұқсат береді. Енді Internet gateways тізімін қарастырайық, сол жақ мәзірден Internet gateways таңдаңыз. Бұл парақшада бір ғана Internet Gateway көрінеді, аты — Lab-IG, күйі Attached — яғни ол VPC-мен байланысқан. Қай VPC екені бағанда көрсетілген — бұл Lab VPC. Енді Security group-тар тізімін қарастырайық, сол жақ мәзірден Security groups бөлімін ашамыз. Бұл парақшада үш Security group бар, олардың бәрі Lab VPC-мен байланысқан. Мысал ретінде алғашқысын қарастырайық. Оны таңдап, төменгі бөлігінде Inbound Rules қойындысын ашайық. Мұнда бір ғана rule бар, ол Lab VPC ішіндегі барлық ресурстан 3306 портына трафикке рұқсат береді. 3306 порты — бұл MySQL және Aurora дерекқорлары үшін стандартты порт. Outbound Rules қойындысын ашсақ, барлық шығыс трафикке рұқсат берілгенін көреміз — бұл да әдепкі ереже. Осылайша біз бірінші тапсырманы аяқтадық, Lab VPC-мен байланысты барлық ресурстарды шолдық. Біз екінші тапсырмаға келдік, бұл тапсырмада Application Load Balancer құрамыз. Ол үшін EC2 сервисіне өту керек, сервис іздеу жолағына EC2 деп енгіземіз. Бірінші сілтемені басамыз, ол бізге қажет сілтеме, сонда EC2 сервисінің басты парақшасына өтеміз. Load Balancer тізіміне жету үшін сол жақ мәзірден Load Balancers бөлімін таңдау қажет. Бұл AWS аккаунтында Load Balancer әлі құрылған жоқ, сондықтан Create Load Balancer батырмасын көреміз. Жоғарғы оң жақтағы не ортадағы кез келген батырманы қолдануға болады — екеуі бір парақшаға апарады. Ендеше, батырманы басайық. Бірінші қадам — Load Balancer түрін таңдау. Біздің жағдайда — Application Load Balancer, сәйкес батырмада Create басамыз. Содан кейін жаңа ресурс деректерін енгізу бетіне өтеміз. Load Balancer Name ретінде Inventory-LB деп көрсетеміз. LB — бұл Load Balancer қысқармасы. Төменге жылжимыз, келесі маңызды бөлім — Network Mapping. Мұнда VPC ретінде Lab VPC таңдаймыз, сосын Availability Zones және сол зоналарға тиесілі subnet-терді көрсету қажет. Енді us-east-1a және us-east-1b зоналарын таңдап, сәйкесінше Public Subnet 1 және Public Subnet 2 subnet-терін көрсетеміз. Келесі бөлім — Security Groups, бізге жаңасын жасау керек, сондықтан сілтемені басамыз. Жаңа Security Group жасау парақшасы жаңа қойындыда ашылады. Security Group Name ретінде Inventory-LB көрсетейік. Description ретінде Enable Web Access to Load Balancer деп көрсетеміз, VPC ретінде Lab VPC таңдаймыз. Содан кейін 2 Inbound Rules жасау қажет. Add Rule батырмасын басып, тип ретінде HTTP, Source ретінде Anywhere таңдаймыз — яғни бүкіл интернет. Дәл солай HTTPS трафик үшін де жасаймыз. Екі Rule құрылған соң, парақшаның соңына дейін жылжып, Create Security Group батырмасын басамыз. Бізді басты ресурс парақшасына қайта бағыттайды және жоғарғы бөлікте ресурс сәтті құрылғаны туралы хабарлама шығады. Енді Load Balancer құрып жатқан қойындыға оралып, Security Groups тізімін жаңарту үшін Refresh батырмасын басу қажет. Тізімнен Inventory-LB Security Group таңдап, әдепкі (Default) Security Group-тен құсбелгіні алып тастаймыз. Келесі бөлім — Listeners and Routing, бұл қай трафиктің қай target group-қа бағытталатынын сипаттайды. Біздің жағдайда бұл HTTP протоколы, 80-порт — стандартты HTTP трафик. Жаңа target group жасау қажет, ол үшін тиісті сілтемені басамыз. Бізді браузердің жаңа қойындысында таргет топты құру қойындысына бағыттайды, мұнда Target type ретінде Instances көрсетеміз. Содан кейін Target group name ретінде Inventory-App деп көрсетеміз, VPC ретінде Lab VPC таңдаймыз және парақшаның соңына дейін жылжимыз. Төменгі бөлігінде Advanced Health Check Settings бөлімі болады, оны ашу керек және келесі мәндерді енгіземіз. Healthy Threshold ретінде ең кіші мән — 2 көрсетеміз, осылайша Load Balancer инстанстар күйінің өзгерісіне тезірек әрекет етеді, интервал да кіші болсын — 10 секунд. Парақшаның соңына дейін жылжып, Next батырмасын басамыз. Таргет топты құрудың екінші парақшасында бізге таргеттерді тіркеу ұсынылады, бірақ әзірше бұл қажет емес. Сондықтан парақшаның соңына дейін жылжып, Create Target Group батырмасын басамыз. Бізді target groups тізімі бар парақшаға бағыттайды және экранның жоғарғы жағында таргет топ сәтті құрылғаны туралы хабарлама көрінеді. Енді Load Balancer құру парақшасына қайта оралуымызға болады. Refresh батырмасын басып, target group тізімін жаңартамыз, содан кейін ашылмалы тізімнен Inventory-App таңдаймыз. Парақшаның соңына дейін жылжып, Summary бөлімін көреміз — мұнда бұған дейін енгізілген барлық параметрлер көрсетіледі. Егер бәрі сәйкес келсе және дұрыс болса, оң жақ төменгі бұрыштағы Create Load Balancer батырмасын басамыз. Бізді Load Balancer сәтті құрылғаны жайлы хабарламасы бар парақшаға бағыттайды. View Load Balancer батырмасын басуға болады, сонда Load Balancers тізімі бар парақша ашылады. Тізімде өз Load Balancer-імізді көреміз және ол Provisioning күйінде, дайын күйге өту үшін біраз минут қажет. Осылайша біз зертханалық жұмыстың екінші тапсырмасын аяқтадық. Load Balancer күйінің өзгеруін күтудің қажеті жоқ, бірден үшінші тапсырмаға өте аламыз. Біз үшінші тапсырмаға келдік, бұл тапсырма аясында Auto Scaling group құрамыз. Auto Scaling group құру үшін алдымен Launch Template болуы керек, Launch Template жасағанда біз кастомды AMI көрсете аламыз. Яғни бұл — барлық қажетті баптаулар жасалған веб-сервердің көшірмесі, біз оны қолдана аламыз. Бұл зертханалық жұмыс аясында бізге веб-сервер жасалғандықтан, сол серверден қазір Image құрамыз. Ол үшін сервис іздеу жолағын қолданып, EC2 деп тереміз. Бірінші сілтеме — бізге қажетті сілтеме, соны басамыз. EC2 сервисінің басты парақшасында инстанстар тізіміне өту керек. Ол үшін сол жақтағы навигациялық мәзірден Instances пунктін таңдаймыз. Инстанстар тізімі бар парақшада бір ғана инстанс көрінеді — Web Server 1. Инстанс Running күйінде екенін көреміз және статус чек те 2 of 2, Checks Passed болуын күтеміз. Егер бәрі дұрыс болса, серверді таңдап, экранның оң жақ жоғарғы бөлігінде Actions батырмасын басамыз, ашылмалы тізімнен Image and Templates → Create Image таңдаймыз. Бізді жаңа image құру парақшасына бағыттайды, Image Name ретінде Web Server AMI, Description ретінде Lab AMI for Web Server деп көрсетеміз және парақшаның соңына дейін жылжимыз. Қалған баптауларды әдепкі бойынша қалдырамыз, Create Image батырмасын басамыз. Бізді инстанстар тізімі бар парақшаға қайта бағыттайды, жоғарғы жағында AMI сәтті құрылғаны туралы хабарлама көрінеді, енді Launch Template жасауға көшеміз. Ол үшін сол жақ мәзірден Launch Templates бөлімін таңдау қажет. Бұл AWS аккаунтында Launch Templates әлі жасалмаған, сондықтан Create Launch Template батырмасы бар парақша көрінеді — соны басу керек. Бізді Launch Template құру парақшасына бағыттайды, мұнда біраз мәліметтер енгізу керек. Launch Template Name ретінде Inventory-LT деп көрсетеміз, LT — Launch Template қысқармасы. Auto Scaling Guidance жанына құсбелгі қойып, төмен қарай жылжимыз. Келесі бөлім — операциялық жүйені немесе AMI таңдауға арналған, My AMIs қойындысын ашып, Owned by me фильтрді қосамыз — бұл өзіміз жасаған AMI тізімін көрсетеді. Тізімнен Web Server AMI тауып, оны таңдаймыз. Сәл төменірек Instance Type ретінде t2.micro таңдаймыз, Key Pair ретінде vockey таңдаймыз. Осы кілттің Private key-ін зертханалық жұмыстың басты парақшасынан жүктеп алуға болады. Келесі бөлім — Network Settings, мұнда Select Existing Security Group таңдаңыз, ашылмалы тізімнен Inventory-App таңдаңыз. Парақшаның соңына дейін жылжып, Advanced Details бөлімін ашыңыз. IAM Instance Profile ретінде EC2 сервисі үшін арнайы жасалған IAM роль таңдаймыз — аты Inventory-App-Role. Сәл төменірек түсіп, Detailed CloudWatch Monitoring іске қосу қажет. Парақшаның ең төменгі бөлігінде User Data енгізуге болады — бұл жаңа EC2 инстанс іске қосылғанда автоматты түрде орындалатын командалар тізімі. Бұл командалардың мақсаты — веб-сервер мен демо қосымшаны жүктеп алып, орнату. Осыдан кейін олар EC2 инстансымызда іске қосылып, сұраныстарды өңдеуге дайын болады. Біз барлық қажетті деректерді енгіздік, енді Create Launch Template батырмасын басуға болады. Бізді Launch Template сәтті құрылғаны туралы хабарламасы бар парақшаға бағыттайды, сол жердегі сілтемені басып, ресурс парақшасына өтуге болады. Енді Auto Scaling group жасауға көшеміз. Ол үшін экранның жоғарғы оң жағындағы Actions батырмасын басып, ашылмалы тізімнен Create Auto Scaling Group таңдаймыз. Бізді жаңа Auto Scaling group жасауға арналған жеке парақшаға бағыттайды. Auto Scaling Group name ретінде Inventory-ASG деп көрсетеміз, ASG — Auto Scaling Group қысқармасы. Launch Template ретінде Inventory-LT таңдаймыз және парақшаның соңына дейін жылжимыз. Келесі парақшада VPC деректерін енгізу қажет — бізде бұл Lab VPC және Availability Zones ретінде us-east-1a және us-east-1b көрсетеміз. Парақшаның соңына дейін жылжып, Next батырмасын басу қажет. Үшінші парақшада бізге Load Balancer-ге байланыс орнату ұсынылады, бұл байланыс тікелей емес, Target топ арқылы жүзеге асады, сондықтан Attach to an Existing Load Balancer опциясын таңдаймыз. Содан кейін Choose from your Load Balancer Target Groups таңдаймыз және ашылмалы тізімнен Inventory-App көрсетеміз. Health Checks бөлімінде Health Check Grace Period үшін 90 секунд мәнін көрсету қажет. Бұл параметрдің мағынасы — EC2 инстанс іске қосылғаннан кейін Auto Scaling group осы инстансты өз құрамына қоспай тұрып 90 секунд күтуі керек. 90 секунд — бұл біздің веб-сервер мен демо қосымшаны жүктеу және орнату командаларын орындауға жеткілікті уақыт. Соңғы бөлім — Additional Settings, мұнда CloudWatch Monitoring қосу қажет және экранның төменгі бөлігінде Next батырмасын басамыз. Осы парақшада біз Auto Scaling group өлшемдерін орнатамыз — Capacity өрістерінің барлығы үшін (Desired, Maximum және Minimum) мән ретінде 2 көрсетеміз. Scaling Policies ретінде None таңдаймыз және төменгі бөліктегі Next батырмасын басамыз. Бұл зертханалық жұмыс аясында біз хабарламаларды баптамаймыз, сондықтан Next батырмасын басамыз. Келесі парақшада тегтерді енгізу ұсынылады, Key және File ретінде Name және Inventory-App көрсетеміз. Біз бұл тегтерді өзіміз жасайтын EC2 инстанстарына қосуға да, қоспауға да болады, біз қосқымыз келеді. Сондықтан, Tag New Instances жолағын белгілеп, экранның төменгі жағындағы Next батырмасын басу керек. Соңғы парақша — Review, мұнда біз енгізген параметрлердің барлығын тексеруге болады. Егер бәрі дұрыс болса, Create Auto Scaling Group батырмасын басамыз. Біз Auto Scaling Groups тізімі бар парақшаға бағытталамыз. Тізімде біздің Auto Scaling Group көрінеді және күйі Updating Capacity болады. Біраз күтіп, парақшаны жаңартсақ, ол қосымша екі инстанс құрып, трафик қабылдауға дайын күйге келеді. Осылайша біз үшінші тапсырманы аяқтадық және келесіге өте аламыз. Біз төртінші тапсырмаға келдік, мұнда біз Security Group баптауларын қауіпсіз ету және Best Practice зерттеу үшін жаңартамыз. Алдымен VPC сервисіне өтіп, сол жақтағы мәзір арқылы Security Groups бөліміне кіреміз. Security Group тізімінен Inventory-App тауып, таңдаймыз. Төменгі бөліктегі Inbound Rules қойындысын ашамыз және ешқандай ереже болмаса, Edit Inbound Rules батырмасын басу қажет. Бізді rules өңдеу бетіне бағыттайды, Add Rule батырмасын басамыз. Жаңа жолда Type ретінде HTTP көрсетеміз, Source ретінде Custom таңдаймыз. Келесі жолда sg деп тере бастаймыз, сонда барлық Security Group көрсетіледі. Бізге Load Balancer-дің Security Group керек, осылайша инстансқа одан трафик келуіне рұқсат береміз — тізімнен Inventory-LB таңдаймыз. Қосымша Description ретінде Traffic from Load Balancer деп жазамыз, не үшін құрылғанын еске түсіру жеңіл болу үшін. Экранның төменгі оң жақ бұрышындағы Save Rules батырмасын басамыз. Бізді қайта Security Group парақшасына бағыттайды, Inbound Rules қойындысында енгізген өзгерістердің сәтті қолданылғанын көреміз. Енді Security Group тізімінде Inventory-App және Inventory-DB топтарынан құсбелгіні алып тастаймыз. Inbound Rules қойындысында Lab VPC ішіндегі кез келген IP-адресінен 3306 портына трафикке рұқсат беретін бір ереже бар екенін көреміз. Бұл жақсы ереже, бірақ оны жақсартуға болады. Оны жаңарту үшін Edit Inbound Rules батырмасын басайық. Inbound Rules өңдеу парақшасында бар жолды өшіріп, Add Rule батырмасын басамыз. Жаңа жол қосылады, Type ретінде MYSQL/Aurora таңдаймыз, онда қажетті протокол және Port range автоматты түрде қойылады — TCP және 3306. Source ретінде Custom таңдаймыз, келесі өрісте sg деп тереміз. Идеясы — дерекқорға тек қосымша серверлерінен кіруге рұқсат беру, сондықтан тізімнен Inventory-App таңдап аламыз. Description ретінде Traffic from Application Servers деп жазып, Save Rules батырмасын басамыз. Бізді қайта Security Group парақшасына бағыттайды, Inbound Rules қойындысында өзгерістер күшіне енгенін көреміз. Осылайша зертханалық жұмыстың төртінші тапсырмасын аяқтадық. Қазір бесінші тапсырманы орындауға көшуге болады. Біз бесінші тапсырмаға келдік және қазір өз қосымшамызды тестілеуге кірісеміз. Сервис іздеу жолағына EC2 деп теріп, осы аттас сервиске өтеміз. EC2 сервисінің басты парақшасында сол жақ мәзір арқылы Target Group тізімін ашу қажет. Осы жерден өз Target топты таңдап, Targets қойындысын ашамыз. Қазір екі таргет бар екенін көреміз, олар екі түрлі availability зонада орналасқан және күйі Healthy. Жақсы, енді сол жақ мәзір арқылы Load Balancer бөліміне өтеміз. Load Balancer-імізді таңдаймыз және Details қойындысында оның DNS name көшіріп аламыз. Осы URL-ді көшіріп, браузердің жаңа қойындысында ашамыз. Қосымша ашылады және бұл сұраныс қандай ID мен availability зонадағы инстанс арқылы өңделгенін көреміз, мысалы — us-east-1b. Егер парақшаны жаңартсақ немесе осы URL-ді басқа браузерде ашсақ, Load Balancer басқа инстансқа бағыттауы мүмкін, нәтижесінде басқа хабарлама көреміз. Бұл жағдайда біз EC2 инстансының басқа ID-н және басқа availability зона — us-east-1a көреміз. Осылайша қосымшамыздың дұрыс орнатылғанын және Load Balancer-дің дұрыс жұмыс істейтінін тексердік. Келесі тапсырмаға өте аламыз. Біз алтыншы тапсырмаға келдік, мұнда IT-инфрақұрылымның жоғары қолжетімділігін тестілеу жүргіземіз. Веб-серверлердің біріндегі ақауды симуляциялау үшін инстанстар тізіміне өтіп, us-east-1a availability зонасындағы Inventory қойындысын таңдаймыз. Содан кейін экранның оң жақ жоғарғы бұрышындағы Instance state батырмасын басып, Terminate instance таңдаймыз. Біз инстансты өшірдік, енді осы EC2 инстанс өңдеген парақша ашық тұрған қойындыға қайта оралайық. Егер біз парақшаны жаңартсақ, қате шығады. Егер біраз күте тұрсақ, Load Balancer бір EC2 инстансында ақау бар екенін түсініп, автоматты түрде оған трафик жіберуді тоқтатады. Сонда барлық трафик екінші EC2 инстансқа бағытталады. Бір минуттан кейін парақшаны жаңартсақ, біздің сұраныс енді басқа availability зонада, яғни us-east-1b орналасқан инстанс арқылы өңделгенін көреміз. Енді AWS Management Console ішінде қандай өзгерістер болғанын тексерейік. Алдымен Target топты ашамыз, өз Target топты таңдап, Targets қойындысына өтеміз. Қазір бізде екі емес, бір ғана таргет бар екенін көреміз — бұл us-east-1b availability зонасындағы инстанс, оның күйі Healthy, сондықтан біз қосымшаның парақшасын сәтті көрдік. Енді Auto Scaling group бөліміне өтейік. Instance Management қойындысында инстанстар тізімін көреміз. Бірінші жол — бұл өзіміз өшірген EC2 инстанс. Auto Scaling group бұл инстанста ақау барын анықтады, оны Unhealthy деп белгілеп, оны өз құрамынан алып тастап, ажырату процесін бастады. Сонымен қатар, үшінші жолда жаңа EC2 инстанс us-east-1a зонасында құрылып жатқанын көреміз — ол ақаулы инстанстың орнын басады және қазір Pending күйінде. Бұл Auto Scaling group оны әлі өз қатарына қоспағанын білдіреді. 90 секундтық Grace period аяқталған соң ол In Service күйіне өтеді. Содан кейін load balancer оған трафик жібере бастайды. Біраз уақыт өткен соң парақшаны жаңартсақ, екі жұмыс істеп тұрған инстансты көреміз — олар екі түрлі availability зонада орналасқан: us-east-1a және us-east-1b. Енді Target топқа қайта оралсақ, екі таргет тіркелгенін көреміз. Бұл — бұрынғы us-east-1b зонасындағы инстанс және жаңадан құрылған us-east-1a зонасындағы инстанс. Екеуінің де күйі Healthy, сондықтан Load Balancer оларға трафик бағыттайды. Осылайша бұл тапсырманы аяқтап, келесіге көшеміз. Біз зертханалық жұмыстың барлық міндетті тапсырмаларын орындадық. Енді екі қосымша тапсырма бар, оларды да орындауға болады. Бірінші қосымша тапсырма — дерекқорымыздың жоғары қолжетімділігін баптау. Біз веб-серверлер үшін жоғары қолжетімділікті орнаттық, және ақау жағдайында трафик автоматты түрде қайта бағытталады, ал Auto Scaling group жаңа инстансты іске қосады. Барлығы автоматты түрде жұмыс істейді, бірақ қазіргі әлсіз жеріміз — дерекқор, себебі ол us-east-1a зонасында орналасқан. Егер дерекқор немесе осы availability зона істен шықса, EC2 инстанстар жұмыс істеп тұрса да, олар қолжетімсіз дерекқорға қосыла алмайды. Сондықтан IT-инфрақұрылымның жоғары қолжетімділігі оның ең әлсіз буынына байланысты. Енді осыны түзетіп, дерекқорды да жоғары қолжетімді етейік. Сервис іздеу жолына RDS деп тереміз, тиісті сілтеме шығады — соған өтеміз. Сол жақ мәзірден Databases бөлімін таңдаймыз. AWS аккаунтындағы барлық дерекқорлар тізімі шығады. Бізге Inventory-DB қажет, оны таңдап, Modify батырмасын басамыз. Бізді дерекқорды өңдеу парақшасына бағыттайды, бізді Availability and durability бөлімі қызықтырады — сонда Create a standby instance таңдаймыз. Оны басқанда жаңа бөлімдер пайда болады, Instance configuration бөлімінде дерекқор типін көрсетеміз — db.t3.small таңдаңыз. Келесі бөлім — деректерге бөлінетін диск кеңістігі, 10 ГБ көрсетеміз де, парақшаның соңына жылжимыз. Экранның төменгі оң жағындағы Continue батырмасын басамыз. Келесі парақшада енгізілген өзгерістер қысқаша көрсетіледі. Екінші бөлімде өзгерістерді қазір енгізу немесе кесте бойынша жасау ұсынылады. Зертханалық жұмыс аясында бізге екінші нұсқа қажет — Apply immediately таңдаймыз да, Modify DB instance батырмасын басамыз. Бізді дерекқорлар тізімі парақшасына қайта бағыттайды, онда біздің дерекқордың күйі Modifying екенін көреміз. Екінші availability зонада жаңа дерекқор инстансы құрылуы үшін біраз уақыт қажет болады. Бізде кластер құрылуда, ол кластерде екі дерекқор инстансы болады. Олар әртүрлі availability зоналарда орналасқан және active-passive принципімен жұмыс істейді. Барлық трафик негізгі availability зонасына бағытталады, егер қандай да бір мәселе туындаса, автоматты түрде басқа availability зонадағы standby instance дерекқорына ауысады. Ол енді негізгі болып саналады және дерекқордың адресі өзгермейтінін ескеріңіз, сондықтан бұл өзгеріс қосымша серверлер үшін байқалмайды. Осылайша біз IT-инфрақұрылымымыздағы әлсіз буынды жойдық және енді дерекқорымыз жоғары қолжетімді. Біз бірінші опционалдық тапсырманы аяқтадық, енді екіншіге өте аламыз. Біз екінші опционалдық тапсырмаға келдік және мұнда NAT gateway үшін жоғары қолжетімділікті орнатамыз. NAT gateway — бұл біздің IT-инфрақұрылымымыздың ең маңызды бөлігі болмаса да, оны қалай орнатуға болатынын көрсетеміз. Кейін жұмыс барысында сіз өзіңіз шешесіз: NAT gateway үшін жоғары қолжетімділік қажет пе, жоқ па. Естеріңізге саламын, NAT gateway — бұл private subnet ішіндегі ресурстарға интернетке шығуға мүмкіндік беретін ресурс. Бұл не үшін керек? Әдетте жаңа ресурсты орнатқанда, ол интернеттен қосымша бағдарламалар мен пакеттерді жүктейді. Осы кезде NAT gateway пайдаланылады — бұл ресурстардың интернетке қауіпсіз шығуын қамтамасыз етеді және сырттан private subnet ішіндегі ресурстарға ешкім жете алмайды. Бізде жаңа ресурстар жиі жасалмайтындықтан, NAT gateway үшін жоғары қолжетімділік әрдайым қажет емес. NAT gateway жасау үшін VPC сервисіне өту қажет. Сервис іздеу жолағын қолданып, аттас сервиске өтеміз. VPC сервисінің басты парақшасында сол жақ мәзірдегі NAT gateway пунктін таңдаймыз. Соны басайық. NAT gateways тізімінде бір ғана ресурс бар, ол Public subnet 1 ішінде орналасқан. Енді Public subnet 2 ішінде орналасатын екінші NAT gateway жасаймыз. Экранның жоғарғы оң жағындағы Create NAT gateway батырмасын басайық. Бізді ресурс құру парақшасына бағыттайды, сәйкес subnet таңдаймыз. Allocate Elastic IP батырмасын басамыз — Elastic IP ресурсы жасалып, автоматты түрде NAT gateway-ге байланады. Осыдан кейін экранның төменгі оң жағындағы Create NAT gateway батырмасын басамыз. Біз NAT gateway басты парақшасына бағытталамыз, тиісті хабарлама пайда болады. Бірақ NAT gateway күйі Pending екенін ескеріңіз. Оның қолжетімді болу үшін біраз уақыт — бірнеше минут қажет. Ол орнатылып жатқан кезде Route tables жаңарта аламыз. Сол жақ мәзірден Route tables пунктін таңдаймыз. Create Route table батырмасын басу қажет болады. Біз жаңа Route table жасаймыз - Private route table 2 деп атаймыз. Оның идеясы — оны private subnet-ке байланыстырып, сол subnet ішіндегі ресурстар интернетке екінші NAT gateway арқылы шыға алуы. VPC өрісінде Lab VPC таңдап, Create route table батырмасын басамыз. Бізді ресурс парақшасына бағыттайды, Routes қойындысын таңдаймыз. VPC ішіндегі ресурстар бір-бірімен байланыса алуы үшін әдепкі route бар екенін көреміз. Енді NAT gateway үшін екінші route қосу қажет — Edit routes батырмасын басамыз. Бізді route өңдеу парақшасына бағыттайды — Add route батырмасын басу қажет. Жаңа жолда Destination ретінде нөлдерден тұратын CIDR блок көрсетеміз — бұл интернет, ал target ретінде NAT gateway таңдаймыз. Қай NAT gateway қажет екенін білмесеңіз, NAT gateways тізімі парақшасына қайтып оралып, қажетті ID-ні қарап, осы парақшадан сол ID-ні таңдаңыз. Барлығы дайын болған соң, Save changes батырмасын басу қажет. Жақсы, енді бұл route table-ді private subnet-ке байлау қажет. Ол үшін Subnet associations қойындысын ашып, Edit subnet associations батырмасын басамыз. Бізді subnet байланысын өңдеу парақшасына бағыттайды. Private subnet 2 таңдап, төменгі оң жақтағы Save associations батырмасын басамыз. Енді Routes қойындысына оралсақ, бізде екі route бар екенін көреміз. Бұл route table біздің subnet-ке байланысты және NAT gateway қолданыста. Осылайша NAT gateway енді жоғары қолжетімді болды. Жақсы, осымен екінші опционалдық тапсырма аяқталды және зертханалық жұмыстың барлық тапсырмалары орындалды. Енді автобағалау скриптін іске қосып, зертханалық сессияны дұрыс аяқтау қажет. Автобағалау скриптін іске қосу үшін зертхана жұмысының басты парақшасында Submit батырмасын басып, бұл әрекетті растау қажет. Біраз уақыттан кейін нәтижелер ашылады — жалпы баллды және тапсырмалар бойынша бөліністі көресіз. Өкінішке қарай, осы зертхана жұмысы үшін бағалау скрипті сәл дұрыс жұмыс істемейді, сондықтан сіз көріп тұрған максималды балл — осы жұмыстағы шек. Зертханалық жұмысты аяқтау үшін экранның жоғарғы оң жағындағы End lab батырмасын басып, әрекетті растау қажет. Біз енді бұл парақшаны жабуға болады деген хабарламаны көреміз және зертхана жұмысынан шығуға болады. Сондай-ақ AWS Management Console-ден дұрыс шығуды ұмытпаңыз. Ол үшін тек бір парақша қалдырып, оның жоғарғы оң жақ бұрышында орналасқан пайдаланушы атын басып, ашылған тізімнен Sign out батырмасын басу қажет. Осымен зертханалық жұмысымыз аяқталды. Біз AWS бұлтында жоғары қолжетімді IT-инфрақұрылымды орнаттық. Сізде туындаған сұрақтарға жауап алды деп үміттенемін. Егер сұрақтар қалса — міндетті түрде қойыңыз, мен қуана жауап беремін. Назарларыңызға рахмет! Келесі белсенділіктерде кездескенше!
